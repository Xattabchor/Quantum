# Control probe exit -6: allocation mismatch hypothesis

E65 Controls v1.0.0 mode 1 and mode 2 reached TO=1 and ended type 0 reason -6; mode 3 panicked 46 before TO. `R:0` was written before cleanup and does not prove successful cleanup. See `symbian9/level41_mda_controls_probe/RUNTIME_RESULTS.md`.

Rebuilt exact v1.0.0 E32 SHA-256 `36b2fe31726b64a8529a811b99e4943b2b9201dfef5e5143dd2f57fc1e70651f`, matching the device package's recorded E32 hash. SDK 0.3.0 `include/platform/e32base.inl` implements `CBase::operator new(TUint)` as `User::AllocZ`; the two probe-owned `CBootstrap` and `CObservation` derive from CActive/CBase. The v1.0.0 ARM ELF symbols and Thumb disassembly show their deleting destructors at 0x8918 and 0x8890 call sized global delete at 0x8B6E. That calls `SymbianRuntimeFree` at 0x8CBC, which tests a magic header before the pointer and calls the exit path with -6 when it fails. Pinned SDK source `hpnkv/symbian-platform` commit `b105f752f84d1b5640052f64c4a703017810d7b8`, `cpp/symbian/runtime/sdk_heap.cc` and `heap.cc`, describes the expected SDK allocation header and failure path via `User::Exit(-6)`. In v1.0.0 worker cleanup, bootstrap is deleted first after saving R. This is a strong, testable explanation for -6, not proof of the exact E65 execution path; data preceding a native allocation could coincidentally pass the header test, and other causes remain possible.

Controls v1.0.1 adds class-specific `operator delete` using `User::Free` to the two probe-owned CActive-derived classes and records cleanup stages K=1..6. Its rebuilt ELF deleting destructors no longer call the global sized-delete stub. All external player/scheduler/cleanup objects keep their existing ownership path; CSession still uses its normal global allocation and delete. Verify mode 1 and mode 2 exit reason and K on E65. A clean result would support, not prove every detail of, the hypothesis. This cleanup issue occurs after timer/stop in modes 1 and 2; it does not establish a causal explanation for panic 46 which occurs earlier in mode 3. The probe change is not applied to game code.
