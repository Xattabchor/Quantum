# E65 minimal MDA probe follow-up

## Observed

Minimal v1.0.0 (SISX SHA-256 `7dc5194c4bb57983ca3dbafb04525d2ba8091ccf7cd3567c95c7f57197a78aeb`) plays audibly and reports worker panic `E32USER-CBase 46`, `O:1 I:0 P:1/1 C:0 E:9999 T:0 TO:0 R:0 S:6`. User confirmed repeated runs still show `Start:0` and produce sound. `R:0` is an initial value on panic; no playback completion was captured. See `symbian9/level41_mda_minimal_probe/RUNTIME_RESULTS.md`.

## Inspection, not a device trace

- In the probe, startup occurs in a one-shot `CBootstrap::RunL`. After it has executed, the bootstrap is not rearmed. Play is called directly in `MapcInitComplete`; there is no explicit `RequestSignal` or `RequestComplete` in probe source. These facts do not exclude an earlier mismatched completion, corruption, SDK runtime behavior or a library request. Telemetry is mutex-protected and changes timing.
- Later kernel source `SymbianSource/oss.FCL.sf.os.kernelhwsrv` commit `0c3208650587ac0230aed8a74e9bddb5288023eb`, `kernel/eka/euser/cbase/ub_act.cpp` `DoRunL`, waits for a request signal and requires an active object with completed status; otherwise it panics. `User::WaitForRequest` in `kernel/eka/euser/us_exec.cpp` restores signals belonging to other requests while waiting. E65 ROM analysis in `scheduler-rom-comparison.md` independently found a structurally similar loop, not a complete source identity. Panic therefore cannot tell us which component signalled or when.
- Later audio source `SymbianSource/oss.FCL.sf.os.mmaudio` commit `a39c075cce88671b23d13598fda2f7cbf008f3bb`, `mmlibs/mmfw/src/Client/Audio/mmfclientaudioplayer.cpp`, `DoPlay` calls controller Prime, SetPosition and Play; `HandleEvent` handles a separate playback-complete event and conditionally calls the client. This is a reference architecture, not proof of the exact E65 implementation or of where this failure occurs.
- Pinned SDK source `hpnkv/symbian-platform` commit `b105f752f84d1b5640052f64c4a703017810d7b8`, `cpp/symbian/runtime/sdk_timer.cc`, contains a `SymbianRuntimeWakeSignal` using `RThread::RequestSignal` and timer wrappers; `concurrency/guest/symbian/concurrency/timer_pump.h` references that wake. However the minimal probe source does not call these wrappers, and their presence in upstream is **not evidence they are linked or executed** in the probe. Establish symbol reachability in the exact built ELF before treating them as a hypothesis. `legacy_atomic_ops.cc` can call `User::After(0)` on contention, but whether those operations occur during this test remains unproven.

## Next discriminating test design — not built or run

Use one fresh worker per mode, same bootstrap, telemetry and finite observation timer (e.g. 3 seconds) in all modes: (1) timer-only, no player; (2) construct/open same WAV and wait after successful init, no Play; (3) same open then Play. Report timer firing, init, play entry/return, completion, worker exit category/reason and sound. The observation timer is an additional active object and changes timing relative to the minimal probe; it is not evidence that a no-panic result fixes the original. A panic only with mode 3 would narrow the trigger to Play or later playback-related activity, but not prove a particular component. A panic in mode 2 would shift attention to opening/init or common infrastructure; mode 1 panic would implicate shared harness/timer/ABI without excluding other defects. A mode that does not complete or whose init fails is inconclusive. Repeat modes, report all results, and separately inspect exact ELF symbol reachability and SDK/E65 ABI. Do not modify game v1.0.53 on these hypotheses alone.
