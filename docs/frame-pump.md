# Отдельный тест цепочки вывода кадра: Frame Pump

Не заменяет игру или `Quantum_EmptyFrame_Test.jar`. Карты, BVH, M3G,
Image-копирования, геометрии и текстур здесь нет. Проверяем две гипотезы:
вклад пробуждения рабочего потока после `paint` и возможность другого
пути вывода через `GameCanvas.flushGraphics()`.

## Что измерено на телефоне до этой сборки

В предыдущем Empty Frame пользователь прислал повторные фотографии.
Все следующие строки — FULL HUD, QUEUED, S0 (вообще без `Thread.sleep`):

| Режим | FPS | I, мс | P, мс | G, мс | Q, мс |
|---|---:|---:|---:|---:|---:|
| Canvas fill, первый | 32.2 | 30.9 | 0.7 | 30.2 | 1.2 |
| Canvas fill, повтор | 32.2 | 31.0 | 0.6 | 30.4 | 1.8 |
| Image copy, первый | 30.2 | 33.1 | 0.8 | 32.3 | 1.5 |
| Image copy, повтор | 29.9 | 33.3 | 0.8 | 32.5 | 1.5 |
| M3G RGBZ, ранее | 26.4 | 37.8 | 7.1 | 30.6 | — |

Общий промежуток около 30 мс сохраняется без M3G и Image.
Это **не** доказательство аппаратного предела 32 FPS или чистого ожидания ОС.
Q около 1–2 мс не объясняет весь G: в G попадают эпилог измерителя,
возврат из callback, завершение/вывод и планирование рабочего потока.
Фотографии относятся к предыдущему тесту, не к новой сборке Frame Pump.

## Три варианта

| Клавиша | Надпись | Цепочка |
|---|---|---|
| **1** | `0 WORKER CANVAS` | `paint` завершает измерение → уведомление → worker → `repaint` |
| **3** | `1 SELF CANVAS` | следующий `repaint` запрашивается непосредственно в конце `paint` |
| **5** | `2 GAME FLUSH` | один worker: заливка управляемого GameCanvas-буфера → HUD → `flushGraphics()` |

В SELF worker припаркован, не будится после каждого кадра и не запрашивает
перерисовку. Canvas допускает не более одного собственного незавершённого
запроса; нет `serviceRepaints()`. В FLUSH нет цикла `paint`/`repaint`, рисует и
вызывает flush один поток. `GameCanvas(false)` сохраняет обычные клавишные
callback, а не подавляет их ради polling.

Во **всех** вариантах S0: нет `sleep`, `yield`, искусственного лимита кадров.
Режим по умолчанию — WORKER, FULL HUD. Заливка, HUD и меняющийся квадрат
одинаковы. Используется полный размер выбранного Canvas; после смены
размера/режима/видимости измерения прогреваются заново.

Другие кнопки: **0** — следующий вариант, **7** — FULL/MIN HUD,
**#** — выход. Обработчики управления и измерение сериализованы, старые
измерения не смешиваются с новым режимом. При паузе/скрытии активный цикл
останавливается, при возврате перезапускается с прогревом без второго worker.
Ошибка flush останавливает измерения и показывает Alert, без скрытого
перехода на Canvas. После закрытия Alert можно выбрать другой режим.

## Что сфотографировать

1. Запустить, ничего не переключать: **WORKER CANVAS**, FULL.
2. Подождать **8–10 секунд**, сделать фото.
3. Нажать **3**, подождать столько же, фото **SELF CANVAS**.
4. Нажать **5**, подождать столько же, фото **GAME FLUSH**.
5. Если есть заметная разница — повторить все три с **7 / MIN**.

На фото нужны FPS, I/P/G и F/U/H/Q. Для первого сравнения не менять HUD
между тремя вариантами. Если появляется FAILED — прислать текст ошибки,
не считать этот режим успешным быстрым выводом.

## Смысл строк

- FPS — частота измеренных callback/итераций flush, **не доказанные обновления LCD**.
- I — начало→начало кадров.
- P — предыдущая измеренная работа: в Canvas тело paint до выхода из него;
  в GameCanvas рисование **и синхронный вызов flush**.
- G — I минус предыдущий P. Точное равенство сумм `I = P + G`, до округления.
  Включает статистику/формирование текста, возврат и планирование/вывод;
  не является отдельным таймером ОС.
- F — заливка, H — HUD с маркером.
- U — wall time `flushGraphics`, уже включён в P; для Canvas `-`.
- Q — запрос→измеряемое начало Canvas callback; для FLUSH `-`.
  Callback без известного запроса не входит в среднее Q.

Числа — средние за 3 секунды после 1 секунды прогрева. Скопирован прежний
проверенный счётчик сопоставления предыдущего P с последующим G.
`currentTimeMillis` грубый: десятые в среднем не означают субмиллисекундный
таймер, ноль не доказывает бесплатность операции. Нет GPU timestamps.
**P/G между Canvas и FLUSH имеют разную границу**: блокировка в flush
попадёт в P/U, а после возврата paint — в G. Сравнивать прежде всего I/FPS,
а не объявлять перенос времени из G в U ускорением.

Быстрый возврат из flush не гарантирует столько же видимых кадров: платформа
может объединять/буферизовать обновления. Отсутствие ускорения тоже не
доказывает аппаратный предел. Перенос в игру допустим только после замеров
на телефоне и отдельной проверки реальной игровой нагрузки.

S0 может повышать нагрузку и расход батареи. Это краткий диагностический
тест, не новая постоянная настройка игры.

## Сборка и проверки

```sh
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar \
  python scripts/build_frame_pump.py --output-dir downloads
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar python tests/frame_pump/run.py
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar python tests/frame_pump/run.py --packaged
python -m unittest tests/resources/test_frame_pump.py tests/resources/test_empty_frame.py
python scripts/verify_render_checkpoints.py
```

Выход: `downloads/Quantum_FramePump_Test.jar`, JAD, JSON отчёт.
Четыре CLDC 47-класса с preverification; SDK-классы не включаются.
393 проверки исходников и 393 проверки упакованного JAR: синтетические
I/P/G, Q, clock rollback, отдельный поток событий, отсутствие flood/вызовов
serviceRepaints, спящий worker в SELF, единственный flush-поток,
переключения/resize, пауза/скрытие/возврат/закрытие, ошибка flush и возврат
к Canvas. API doubles не моделируют нативную растеризацию или скорость.
Отчёт `handset_tested=false` относится к **новой** сборке; замеров её FPS на
телефоне при публикации ещё нет. Прежние игровые JAR и Empty Frame неизменны.
