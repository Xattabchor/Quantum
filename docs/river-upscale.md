# Карта с рекой: доставка кадра — чёрные полосы или апскейл (DIR / UP)

Отдельный MIDlet: [JAR](../downloads/Quantum_RiverMap_Upscale.jar) ·
[JAD](../downloads/Quantum_RiverMap_Upscale.jad) ·
[отчёт](../downloads/Quantum_RiverMap_Upscale.build-report.json).

Эта сборка — непосредственное продолжение
[pixel-диагностики](river-pixel.md) после её телефонного результата.
Renderer и карта те же самые: классы `RiverPixelMesh`/`RiverPixelStats`
упакованы **побайтно** из опубликованного `Quantum_RiverMap_Pixel.jar`,
базой остаётся неизменный Perspective-родитель. Геометрия, GRID-отбор,
текстуры, свет, река, near128/far60000/FOV74/DMODE9, alpha/depth и pump —
прежние. Меняется только **доставка** готового кадра на экран.

## Что уже измерено на телефоне (та же поза, тот же JAR-родитель)

| Режим | R, мс |
|---|---:|
| S100 TEX SM B | 109 |
| S100 TEX SM M | 103 |
| S75 TEX SM B / M | 75 / 71 |
| S75 1X1 SM B | 64 |
| S75 TEX FL B | 66 |
| S75 1X1 FL B | 55 |
| S50 TEX SM M / B | 48 / 51 |
| S25 | 32 |

Из четырёх масштабов выведена линейная модель
**R ≈ 30 мс фикс + ~74 мс × площадь экрана**, и разложение филла на полном
экране: текстура ~20 мс, интерполяция цвета ~16 мс, глубина+итерация+запись
~42 мс. Единственный рычаг, режущий всё сразу, — площадь кадра. Но `S50 UP`
на телефоне виден не был: раньше уменьшенный viewport оставался в углу с
чёрными полосами.

## Что проверяет эта сборка

Целевой для игры вариант — рендерить мир в уменьшенный viewport и растягивать
на весь экран самым дешёвым способом. На E65/MIDP 2.0 произвольного
scale-блиттера нет, поэтому UP — это `Image.getRGB` + целочисленный
nearest-neighbour expand на Java + `Graphics.drawRGB` без альфы:

```
dst(x,y) = src(floor(x*sw/dw), floor(y*sh/dh))
```

Строки, попадающие на тот же источник, копируются `arraycopy` без повторной
распаковки; буферы заводятся один раз на смену масштаба, не на кадр.
Из FramePump уже известно, что полноэкранная `drawImage`-копия сама по себе
мелкая (~1 мс); неизвестна цена именно Java-цикла распаковки на этом устройстве.
Меряемое окно **C** — полная стоимость доставки: в DIR это полосы+`drawImage`,
в UP это `getRGB`+expand+`drawRGB`.

Вопрос на телефон: `C_UP` при S50 заметно меньше сэкономленных ~55 мс
заполнения (R109→R48-51)? Если да — остаётся живой запас на full-screen
картинку и апскейл рентабелен. Прогноз сходимости по модели: R не меняется
между DIR и UP при том же масштабе, выигрыш/проигрыш виден прямо в C и I.

## Режимы и клавиши

HUD — две строки: режим/FPS и `N/R/C/I`. Подпись режима вида
`S50 UP TEX SM B` = масштаб 50%, апскейл, атлас, SMOOTH, base-level.
`S100 UP` намеренно равен DIR (та же 1:1 `drawImage`) — контроль конвейера,
а не ускорение.

- **1** — BASE: `S100 DIR TEX SM B`;
- **0** — цикл масштаба 100 → 75 → 50 → 25 (остальное сохраняется);
- **3** — доставка DIR ↔ UP (главный A/B);
- **7** — атлас ↔ текстура 1×1 (наследие pixel-диагностики);
- **9** — SMOOTH ↔ FLAT;
- **`*`** — BASE_LEVEL ↔ ближайший mip-уровень;
- **5** — домашняя камера, переключатели сохраняются;
- **2/8/4/6** — движение/поворот; **#** — выход.

## Что снять на телефоне

В одной неподвижной позе (та же близкая к стене, где снимали pixel-тест):

1. `S100 DIR TEX SM B` и `S100 UP TEX SM B` — контроль, что конвейер не
   стал дороже сам по себе;
2. `S75 DIR` → `S75 UP` → `S75 DIR`;
3. `S50 DIR` → `S50 UP` → `S50 DIR` — главная серия: смотреть **R, C, I**;
4. по желанию `S25 DIR/UP`.

По 8–10 секунд на режим, после прогрева; записывать R/C/I из второй строки.
Как и раньше: это Java wall-clock API числа, не GPU timestamps и не
гарантированные LCD flips; FPS полной игры по этому JAR не прогнозируется.

## Телефонный результат (Nokia E65, та же близкая поза)

| Режим | FPS | N | R | C | I |
|---|---:|---:|---:|---:|---:|
| S100 DIR TEX SM B | 7.0 | 120 | 112 | 0 | 141 |
| S100 UP TEX SM B | 7.1 | 119 | 110 | 0 | 140 |
| S75 DIR | 9.1 | 84 | 79 | 0 | 109 |
| S75 UP | 7.1 | 85 | 78 | ~31 (по ΔI) | 140 |
| S50 DIR | 12.7 | 55 | 51 | 0 | 78 |
| S50 UP | 9.1 | 55 | 50 | 33 | 109 |
| S25 DIR | 16 | 36 | 32 | 0 | 62 |
| S25 UP | ~12.8 | 36 | 33 | 24 | 78 |

S100 UP = S100 DIR в пределах шума: контроль чистый. R между DIR и UP
при одном масштабе не меняется (79/78, 51/50, 32/33) — рендер идентичен,
вся цена апскейла в C. Цена full-screen записи ~33 мс при S50, ~24 при S25,
~31 при S75: доминирует запись 240×320, а не чтение источника.

Сводка по режимам относительно S100 DIR (I 141):

- **S50+UP: I 109 (−32 мс, FPS 9.1)** — единственный рентабельный
  full-screen вариант; цена — ×2 зернистость.
- **S75+UP: I 140 (−1)** — экономия филла ≈ цене апскейла, мёртвая точка.
- **S25+UP: I 78 (FPS ~12.8)** — максимальная скорость, ×4 крупнозерно.
- DIR остаётся эталоном качества картинки.

Следствие для боевого кода: апскейл рентабелен только при заметной экономии
филла (≥ 2× уменьшение площади), иначе константная ~30+ мс выдача кадра её
съедает. При S50 новый ограничитель — фикс ~30 мс геометрии/setup (теперь
~60% R): следующий кандидат — сокращение числа поданных треугольников
(чанк-LOD/отбор), которое на S100 не давало эффекта из-за доминирования филла.

## Тулчейн-сноска

Эфемерный тулчейн был восстановлен заново (jdk4py, ECJ 3.16.0 из
npm `coc-java@1.0.0`, API/ProGuard из `vipaoL/j2me-build-tools`).
Пересборка `Quantum_RiverMap_Pixel` из неизменных исходников совпала
побайтно по 209/210 entries; единственное отличие в
`RiverPixelPreview$Viewer.class`: прежний тулчейн привязал унаследованные
`getWidth/getHeight` к классу-потомку, восстановленный ECJ — к объявляющему
`Displayable`; обе ссылки одинаково разрешаются на настоящем MIDP 2.0.
Поэтому здесь шесть renderer/stats классов взяты побайтно из опубликованного
pixel JAR, а их превью-классы в новый JAR не входят. Прежние JAR/игра не
тронуты; ускорение до телефонного A/B не обещается.
