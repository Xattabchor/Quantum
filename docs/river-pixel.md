# Карта с рекой: цена пикселя — масштаб, текстура, shading, mip

Отдельный MIDlet: [JAR](../downloads/Quantum_RiverMap_Pixel.jar) ·
[JAD](../downloads/Quantum_RiverMap_Pixel.jad) ·
[отчёт](../downloads/Quantum_RiverMap_Pixel.build-report.json).

Эта сборка продолжает Overdraw-тест после телефонного результата, где
`A LARGE` оказался быстрее компактных пакетов, front-to-back не дал выигрыша,
а depth prepass резко замедлил кадр. Здесь за основу взят именно быстрый
`A LARGE` путь Perspective: те же крупные per-material VertexBuffer, тот же
GRID-отбор и порядок граней, та же карта с рекой, свет, текстуры, near128,
far60000, FOV74, DMODE9, alpha/depth и перспективная коррекция ON.

Меняется только пиксельная работа внутри `Graphics3D.render`:

- размер native viewport/Image;
- источник текстуры: исходный атлас или диагностическая белая 1×1;
- `PolygonMode` SMOOTH или FLAT;
- level filter текстур: BASE_LEVEL или NEAREST (ближайший mip-уровень).

## Почему этот тест

На телефоне уже получены две крайние точки одной карты:

| Ракурс GRID | T | S | N | I/FPS |
|---|---:|---:|---:|---:|
| Тяжёлая поза, геометрия почти на весь экран | 997 | 2087 | 76 мс | 93 мс / 10,6 с MIN HUD |
| Дальняя полоса геометрии | 930 | 1922 | **38 мс** | **58 мс / 17,2** |

Треугольников во второй точке меньше всего на 7%, а native-рендер дешевле
вдвое. В тяжёлой позе прежняя stage-разбивка давала `R69` из `N77`.
Overdraw-сборка затем показала на близком доме: A LARGE `R108`,
C ORIG `R122`, C F2B `R126`, C ZPRE `R201`. Порядок подачи и prepass
закрыты как направления для E65; осталось разделить площадь закраски и
стоимость одного фрагмента.

## Режимы и клавиши

Живой HUD всегда две строки: режим/FPS и `N/R/I`. Подпись режима вида
`S75 1X1 FL M` означает: масштаб 75%, текстура 1×1, FLAT, mip-фильтр.

| Клавиша | Действие |
|---|---|
| **1** | BASE: `S100 TEX SM B` — полный viewport, атлас, SMOOTH, BASE_LEVEL |
| **0** | цикл масштаба viewport: 100% → 75% → 50% → 25% → 100% |
| **3** | сразу масштаб 50% |
| **7** | текстура: атлас `TEX` ↔ белая `1X1`, модулированная baked-цветами вершин |
| **9** | shading: `SM` smooth ↔ `FL` flat |
| **`*`** | level filter: `B` BASE_LEVEL ↔ `M` NEAREST (ближайший mip-уровень) |
| **5** | home/START; масштаб и пиксельные переключатели сохраняются |
| **2/8**, **4/6** | движение и поворот; стрейфа нет, 7/9 заняты переключателями |
| **#** | выход |

Масштаб — линейный: S75 означает 75% ширины и высоты, то есть 56,25%
пикселей; S50 — 25% пикселей; S25 — 6,25%. Native Image/viewport реально
меньше, фокусные расстояния масштабируются пропорционально, картинка
выводится 1:1 в левый верхний угол, остаток Canvas — чёрные полосы справа
и снизу. Это диагностика native fill, а не готовый полноэкранный upscale.

В `1X1` картинка намеренно становится серой по baked-свету, а alpha threshold
вынужденно 0: режим измеряет цену выборки атласа/alpha, а не предлагает
релизный вид. Река сохраняет геометрию, проход, скорость и кадры анимации,
но сэмплит тот же белый тексель вместо своих BMP.

## Как снимать

Сначала тяжёлая неподвижная поза (стартовая или близкий дом), по 8–10 секунд:

1. **1 → BASE** (`S100 TEX SM B`) — фото.
2. **0 → S75** — фото.
3. **0 → S50** (или сразу **3**) — фото.
4. **0 → S25** — фото.
5. **1 → BASE**, затем **7 → 1X1** — фото.
6. **7 → TEX**, затем **9 → FL** — фото.
7. **9 → SM**, затем **`*` → M** — фото.
8. По желанию собрать комбинацию из выигравших переключателей и повторить BASE.

Между режимами не двигаться. На фото нужны подпись режима и `FPS/N/R/I`.
Главный показатель — **R**: это цикл `Graphics3D.render` внутри N.

Интерпретация:

- R падает примерно с площадью viewport — доминируют framebuffer/depth/
  интерполяция по пикселям; релизный рычаг — внутренний масштаб/letterbox.
- Сильно падает на `1X1` — дорога выборка атласа, его кэш-локальность или
  alpha; дальше имеют смысл mip, меньшие текстуры и разделение opaque/alpha.
- Падает на `M`, особенно в дальнем ракурсе, — минификация без мипов бьёт
  по кэшу; если не падает, реализация могла проигнорировать hint.
- Падает на `FL` — заметна цена попиксельной интерполяции цвета.
- Если при S25 R всё ещё большой, значит внутри R велика непропорциональная
  пикселям часть: вершины/setup/strips или фиксированная синхронизация драйвера.

## M3G 1.0 на E65

Используются только базовые переключатели `Texture2D.setFiltering` и
`PolygonMode.setShading`; отдельного константного `FILTER_MIPMAP` в JSR-184
нет — ближайший mip-уровень выбирается значением `FILTER_NEAREST` именно как
level filter. Фильтрация по спецификации является hint и может игнорироваться
реализацией, поэтому режим `M` требует телефонной проверки. Новых M3G 1.1
hint/getter-путей сборка не вводит.

## Сборка и проверки

```sh
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar \
  python scripts/build_river_pixel.py --output-dir downloads
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar python tests/river_pixel/run.py
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar python tests/river_pixel/run.py --packaged
python -m unittest tests/resources/test_river_pixel.py
python scripts/verify_render_checkpoints.py
```

Проверены исходники и готовый CLDC JAR: по **2102 checks / 144 poses/river
frames**. Контракты подтверждают: BASE побайтно совпадает по draw stream с
immutable Perspective; S50/S25 меняют только viewport при тех же T/S/DC/VB;
`1X1`, FLAT и MIP не меняют геометрию, индексы, порядок и счётчики подачи;
комбинация всех переключателей сохраняет тот же поток геометрии; возврат в
BASE восстанавливает исходный поток; в неподвижной позе нет hot
vertex/index/texture uploads; живой HUD — ровно 2 строки. Desktop doubles не
растеризуют M3G и не измеряют телефонный FPS.
