# Карта с рекой: влияние диагностического HUD FULL / MIN / OFF

Отдельный MIDlet: [JAR](../downloads/Quantum_RiverMap_Hud.jar) ·
[JAD](../downloads/Quantum_RiverMap_Hud.jad) ·
[отчёт](../downloads/Quantum_RiverMap_Hud.build-report.json).

Это тот же world-only просмотрщик старой деревни/карты с рекой, что и в
Perspective/Tex3 тестах, а не замена полной игры. База — неизменяемый
`Quantum_StaticRoom_Perspective.jar`: `maps/kordos/kordos.3d`, запечённый
`lightmap/kordod.vla`, Tex3-материалы forest / `map-selo1.png` / анимированная
река. Геометрия, UV, свет, текстуры, порядок граней, GRID4×4, near128,
far60000, FOV74, DMODE9, alpha/depth и перспективная коррекция ON не меняются.
Классы `StaticRoomPerspectiveMesh` и `StaticRoomPerspectiveStats` взяты из
родителя побайтно; добавлены только два класса нового просмотрщика и manifest.

## Зачем этот тест

В Frame Pump на телефоне сокращение HUD с девяти строк до двух почти удвоило
callback FPS пустого теста: повтор SELF дал FULL 37.7 FPS / I26.4мс и
MIN 74.1 FPS / I13.4мс. Это не доказывает такой же эффект на карте. Здесь
проверяем только вклад самого диагностического оверлея на реальной карте с
рекой при прежнем renderer и прежнем pump `repaint()+serviceRepaints()+sleep(1)`.

## Режимы HUD

| Клавиша | Режим | Что рисуется после копирования карты на Canvas |
|---|---|---|
| **1** | `RIVER FULL` | чёрная панель 90px и 6 строк каждый кадр |
| **3** | `RIVER MIN` | чёрная панель 30px и 2 строки: заголовок + `N/C/I` |
| **0** | `RIVER OFF` | ни панели, ни текста; статистика всё равно собирается |
| **`*`** в OFF | результат | останавливает замер и показывает последний полный результат поверх последнего кадра |
| **`*`** повторно | продолжить | скрывает результат и начинает OFF-замер заново с прогрева |
| **5** | home | исходная камера START/yaw0; выбранный HUD сохраняется, статистика сбрасывается |
| **2/8**, **4/6**, **7/9** | движение | как в прежних просмотрщиках; в замороженном результате движение игнорируется |
| **#** | выход | завершает MIDlet |

По умолчанию запускается **FULL** в исходной позе. Переключение HUD
останавливает движение, сохраняет позу/поверхность и сбрасывает окно статистики:
1с прогрева, затем окно не короче 3с. В OFF строки результата формируются
только при завершении такого окна, а не каждый кадр; замороженный показ по `*`
уже не входит в замер.

## Как снимать на телефоне

1. Запустить и не двигаться. Дождаться числового `RIVER FULL FPS` и ещё одного
   обновления окна (обычно около 8 секунд), сделать фото.
2. Нажать **3** (`RIVER MIN`), снова подождать около 8 секунд, фото.
3. Нажать **0** (`RIVER OFF`): останется только карта без панели. Подождать
   8–10 секунд, нажать **`*`** и сфотографировать замороженный результат.
4. Для контроля нажать **1** и повторить FULL в той же позе.

Между сравниваемыми режимами не двигать камеру. Если поза изменилась, нажать
**5** и начать последовательность заново. На фото нужны FPS, `N/C/I`,
`T/DC/VB`, `S/V/CUT` и `J/B/K/R/E`. Для OFF фото делается только после `*`.

## Смысл счётчиков

- `FPS` — десятые FPS оконного счётчика просмотрщика, не доказанная частота LCD.
- `N` — wall time native render-транзакции в Image; `C` — `drawImage` на Canvas;
  `I` — интервал начала кадров.
- `T/DC/VB` — поданные треугольники, API draw calls и вместимость поданных VB.
- `S/V/CUT` — поданные углы, проверки ячеек и отвергнутые ячейки GRID.
- `J/B/K/R/E` — подготовка/видимость, bind, камера/state/clear, render loop,
  release. Это Java API wall time, не GPU timestamps.

Если OFF/MIN заметно быстрее FULL при тех же `T/DC/VB` и позе, это покажет вклад
диагностического оверлея именно в этом пути. Это ещё не обещание такого же
ускорения полной игры и не объяснение внутреннего механизма платформы. Если
разницы почти нет, значит на этой карте доминирует не HUD, а остальной путь.

## Сборка и проверки

```sh
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar \
  python scripts/build_river_map_hud.py --output-dir downloads
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar python tests/river_map_hud/run.py
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar python tests/river_map_hud/run.py --packaged
python -m unittest tests/resources/test_river_map_hud.py
python scripts/verify_render_checkpoints.py
```

Проверены исходники и готовый CLDC JAR: по **1114 checks / 144 poses/river
frames**. Контракты подтверждают 4750 triangles / 10032 native corners, три
пакета, четыре кадра реки, отсутствие hot vertex/texture uploads в неподвижных
повторах, FULL=6 строк, MIN=2 строки, OFF=0 строк/панелей, замороженный результат
без native render, сохранение позы/поверхности при переключениях и release
target при native API ошибках. Desktop doubles не растеризуют M3G и не измеряют
телефонный FPS.
