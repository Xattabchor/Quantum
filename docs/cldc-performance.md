# Проверка Quantum на klaxons1/j2me_cldc

Дата: **17 октября 2026**.

## Итог

**KVM из указанного репозитория действительно запущен.** Выполнены CPU-микробенчмарки
методов из готового `downloads/Quantum.jar`, без изменения игрового кода и без
заглушек MIDP/M3G. Это **не замер FPS игры и не тест аппаратного M3G**.

Полноценный запуск текущего Quantum на этой Linux-поставке заблокирован:

- `javax.microedition.m3g.Graphics3D` отсутствует (`ClassNotFoundException`).
- Обычный `bin/linux/kvm` не загружает MIDP `Display` даже с поставленными
  MIDP-классами в classpath: `Cannot create class in system package`.
  `Class.forName("code.utils.Main")` завершается такой же ошибкой.
- В текущем Quantum JAR **нет игровых ресурсов**: в `res/` только README.
  Даже другой полноценный MIDP/M3G runtime не заменит отсутствующий уровень и ресурсы.

Наличие исходников MIDP в репозитории не означает, что standalone Linux KVM
содержит их нативную реализацию. Ограничение загрузки `java.*`/`javax.*` видно в
`kvm/VmCommon/h/main.h` (`IS_RESTRICTED_PACKAGE_NAME`) и `kvm/VmCommon/src/loader.c`.
Защита VM не отключалась; графический API фиктивной реализацией не подменялся.

## Результаты CPU-микробенчмарков

Для каждой задачи запускается отдельный процесс KVM. До измерения выполняются
инициализация и проверки результатов, подбор числа повторений до ≥250 мс,
затем дополнительный прогрев. Далее — **5 измерений**; в таблице медиана и
минимум–максимум, делённые на число повторений. Это миллисекунды **на указанную
нагрузку**, не на игровой кадр. Расход измерительного цикла не вычитался.

| Нагрузка | Медиана, мс | Мин.–макс., мс |
|---|---:|---:|
| 1000 вершин: `Vertex.transform` + `project` | 0.814 | 0.809–0.828 |
| 1000 умножений `Matrix.mul` | 1.711 | 1.703–1.789 |
| 1000 треугольников: `Mode5WeaponLight.pack` | 8.500 | 8.406–8.500 |
| 1000 вычислений базового CPU-света `mode5Shade` | 3.055 | 3.039–3.055 |
| 1000 вершин: CPU `Mode5WeaponLight.shade` с активным OMNI | 9.844 | 9.844–9.969 |
| Один CPU-проход `FrameEffects.render`, 240×320 | 50.875 | 50.500–51.125 |
| Один CPU-проход `FrameEffects.render`, 176×220 | 25.938 | 25.938–26.062 |

Условия синтетические: массивы переиспользуются; матрицы/нормали фиксированы.
`pack` многократно обрабатывает один и тот же треугольник из трёх проецированных
вершин, без отправки в GPU. Для CPU OMNI зафиксирована фаза импульса 30/120 мс,
чтобы затухание не меняло нагрузку во время измерений.

В постэффекте включены маска и красный фильтр урона. Это прямой вызов реального
CPU recovery, **не native MODULATE**. Framebuffer переиспользуется без повторной
отрисовки мира; многократное умножение постепенно делает его чёрным. Заполнение
мира и LCDUI flush в это время **не входят**. Внутри измеряемых Java-циклов нет
явного создания новых объектов; печать и настройка выполняются вне таймера.

### Что из этого следует

- Самый дорогой из измеренных участков — **полноэкранный CPU recovery постэффекта**.
  При уменьшении числа пикселей примерно вдвое время этого метода также
  уменьшается примерно вдвое. Это не говорит о стоимости native M3G-прохода.
- CPU-вычисление света с активным OMNI здесь примерно в **3.2 раза** дороже
  базовой CPU-функции света. В нормальном native M3G этот `shade` не заменяет
  аппаратный Light: замер относится к CPU recovery, не к работе GPU.
- Метрическая упаковка позиций для OMNI имеет измеримую CPU-стоимость.
  Таблица не включает остальные стадии подготовки native-пакета.
- **Ускорение FPS после удаления фейкового additive-спрайта этим запуском
  не измерено**: нет полноценной M3G-сцены и сравнения двух игровых прогонов.
- Нельзя пересчитать эти времена на телефон 220 МГц простым отношением частот:
  отличаются CPU, VM, память, графический драйвер и способ вывода изображения.

Не измерены растеризация уровня, AI/физика, звук, погода в полном игровом цикле,
native draw/upload/readback, LCDUI presentation и реальный FPS.

## Воспроизведение

Сначала выполнить обычную SDK-сборку `scripts/build_cldc.py`, чтобы получить
`build/cldc/api.jar`. Нужны Java и ECJ с поддержкой Java 1.3, как для основной
сборки. Затем распаковать указанную ревизию `j2me_cldc` в ignored `build/`:

```sh
mkdir -p build/cldc-perf
curl -L --fail \
  https://codeload.github.com/klaxons1/j2me_cldc/tar.gz/9363b7152b3f3b367eb17a97195ebf035595fed1 \
  -o build/cldc-perf/cldc.tar.gz
tar -xzf build/cldc-perf/cldc.tar.gz -C build/cldc-perf

JAVA=/path/to/java ECJ_JAR=/path/to/ecj-legacy.jar \
python tests/cldc_perf/run.py \
  --cldc-root build/cldc-perf/j2me_cldc-9363b7152b3f3b367eb17a97195ebf035595fed1
```

Если системного 32-битного runtime нет, можно распаковать пакет выше локально
через `dpkg-deb -x` и добавить параметры (ничего не устанавливая в систему):

```sh
  --loader build/cldc-perf/libc32/lib/ld-linux.so.2 \
  --library-path build/cldc-perf/libc32/lib
```

Runner компилирует только тестовый класс, затем использует `bin/linux/preverify`
из указанного репозитория. Игра берётся из существующего JAR. Никакие тестовые
классы не попадают в production JAR. Есть таймаут на каждый процесс.

- [Сводные измерения и SHA-256](benchmarks/cldc-kvm-2026-10-17.json).
- [Сырые выводы процессов, все 5 samples](benchmarks/cldc-kvm-2026-10-17-raw.json).
- Runner: `tests/cldc_perf/run.py`; Java-код: `tests/cldc_perf/KvmPerformance.java`.

Для замера **игрового M3G FPS** всё ещё нужны полный набор ресурсов и runtime с
настоящей JSR-184 (либо целевой телефон), одна и та же сцена и настройки,
отдельные замеры без выстрелов/с выстрелами, с погодой/без неё и с post-effect.
