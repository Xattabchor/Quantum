# Карта с рекой: снижение overdraw — front-to-back пакеты и depth prepass

Отдельный MIDlet: [JAR](../downloads/Quantum_RiverMap_Overdraw.jar) ·
[JAD](../downloads/Quantum_RiverMap_Overdraw.jad) ·
[отчёт](../downloads/Quantum_RiverMap_Overdraw.build-report.json).

База — неизменяемый Tex3 с той же старой деревней/картой с рекой:
`maps/kordos/kordos.3d`, запечённый `lightmap/kordod.vla`, материалы
forest / `map-selo1.png` / анимированная река. Геометрия, UV, свет, текстуры,
порядок исходных граней внутри пакетов, near128, far60000, FOV74, DMODE9,
alpha/depth и перспективная коррекция ON не меняются. Отбор граней везде
прежний GRID; BVH в этом тесте явно выключен, чтобы не смешивать эффекты.

## Почему именно overdraw

Телефонные замеры GRID на одной карте:

| Ракурс | T | S | DC | N | I/FPS |
|---|---:|---:|---:|---:|---:|
| Тяжёлая стартовая поза | 997 | 2087 | 2 | 76 мс | 93 мс / 10,6 с MIN HUD |
| Дальний ракурс, геометрия полосой | 930 | 1922 | 3 | **38 мс** | **58 мс / 17,2** |

Треугольников меньше всего на 7%, углов — на 8%, draw calls даже больше,
а native-рендер вдвое дешевле. BVH в тяжёлой позе резал `T` 997→401 без
изменения `N`. Значит, главный резерв — не число треугольников и не отбор,
а пиксельная работа: сколько фрагментов реально закрашивается и сколько раз
один пиксель перекрывается. Эта сборка атакует именно порядок подачи и
повторную закраску скрытых фрагментов.

## Режимы

По умолчанию запускается **C F2B**.

| Клавиша | Режим | Что меняется |
|---|---|---|
| **1** | `A LARGE` | прежние крупные per-material VertexBuffer, исходный порядок — контроль |
| **3** | `C ORIG` | компактные пространственные пакеты ≤512 углов, исходный порядок пакетов |
| **7** | `C F2B` | те же пакеты и те же вызовы, но непрозрачные пакеты подаются **спереди назад** |
| **9** | `C ZPRE` | C F2B + сначала depth-only проход, затем цветной проход без записи глубины |
| **0** | цикл | A → C ORIG → C F2B → C ZPRE |
| **`*`** | результат | заморозить кадр и показать полные счётчики; повторно — продолжить с прогревом |
| **5** | home | исходная камера START/yaw0, режим сохраняется |
| **2/8**, **4/6** | движение/поворот | стрейфа нет: 7/9 заняты режимами |
| **#** | выход | завершает MIDlet |

Живой HUD специально оставлен минимальным — две строки: режим/FPS и
`N/R/I`, чтобы сам счётчик не добавлял лишний такт выдачи кадра. Полные
`T/DC/VB`, `S/V/CUT/P` и `J/B/K/R/E` смотреть через замороженный `*`.

## Как работает F2B

Компактные пакеты — прежние точные срезы родительских буферов из Packets:
непрерывные пространственно-локальные участки исходного порядка граней, без
переквантования XYZ/UV/RGBA. Для каждого пакета при загрузке считается его
world AABB. Каждый кадр после прежнего GRID-отбора выбранные непрозрачные
пакеты стабильно сортируются по ближайшей глубине AABB вдоль взгляда камеры.
Сортировка выполняется в prepare-фазе (`J`) по заранее выделенным массивам;
индексы, вершины и текстуры в горячем кадре не перестраиваются.

Река (mode7, MODULATE) не сортируется и по-прежнему рисуется после
непрозрачных пакетов в исходном порядке. Внутри пакета порядок strips
прежний. Единственный визуальный риск — победитель на точно копланарных
перекрывающихся гранях из разных пакетов может отличаться из-за квантования
глубины; на телефоне надо смотреть мерцание/артефакты.

## Как работает ZPRE

`C ZPRE` добавляет к F2B классический depth prepass средствами JSR-184:

1. Непрозрачные пакеты рисуются с `colorWrite=false`, `alphaWrite=false`,
   depth test/write ON. Cutout-пакеты сохраняют текстуру и alpha threshold,
   чтобы прозрачные пиксели не писали глубину; полностью непрозрачные идут
   без текстуры.
2. Те же пакеты рисуются цветом с depth test ON и depth write OFF.
   Тест глубины в M3G — LEQUAL, поэтому фрагмент с равной глубиной проходит.
3. Река рисуется как раньше и в prepass не участвует.

Prepass удваивает opaque draw calls и подачу вершин, поэтому на программном
растеризаторе он **может оказаться медленнее**. Он включён отдельным режимом,
а не по умолчанию: если скрытая текстурированная закраска дорогая, ZPRE
выиграет; если доминирует setup/сканирование треугольников — проиграет F2B.

## Совместимость с E65 / M3G 1.0

Пользователь уточнил: на Nokia E65 — **M3G 1.0**. Сборка не использует
M3G 1.1 `OVERWRITE` hint и не вводит новых путей рендера: тот же immediate
mode `Graphics3D.render(VertexBuffer, IndexBuffer, Appearance, null)`,
`bindTarget(..., true, 0)`, прежние Appearance/PolygonMode/Texture2D.
Маски записи цвета/альфы и LEQUAL depth test относятся к базовому JSR-184;
тем не менее именно ZPRE надо первым проверить на телефоне на предмет
ошибок/артефактов конкретной реализации.

## Как снимать

В одной неподвижной тяжёлой позе, по 8–10 секунд на режим:

1. Запуск — **C F2B**: фото живого HUD (`FPS`, `N/R/I`).
2. **3 → C ORIG**: фото.
3. **1 → A LARGE**: фото.
4. **7 → C F2B**: контрольный повтор.
5. По желанию **9 → C ZPRE**: фото; отдельно отметить артефакты/мерцание.

Если нужны `T/DC/VB/J/B/K/R/E`, после живого фото нажать **`*`** и снять
замороженный результат, затем **`*`** ещё раз для продолжения. Между
режимами не двигаться. Сравнивать прежде всего **R**, затем N/I/FPS:

- F2B быстрее C ORIG при тех же T/DC/VB — порядок подачи и ранний depth
  reject работают;
- C ORIG быстрее A — компактные буферы сами по себе дешевле для драйвера;
- ZPRE быстрее F2B несмотря на удвоенные calls/VB — скрытая закраска
  действительно дорогая; если медленнее, prepass на этом программном
  растеризаторе не окупается.

## Сборка и проверки

```sh
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar \
  python scripts/build_river_overdraw.py --output-dir downloads
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar python tests/river_overdraw/run.py
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar python tests/river_overdraw/run.py --packaged
python -m unittest tests/resources/test_river_overdraw.py
python scripts/verify_render_checkpoints.py
```

Проверены исходники и готовый CLDC JAR: по **7 452 080 checks / 144
poses/river frames**. Контракты подтверждают: A побайтно совпадает с
immutable Tex3 draw stream; C ORIG подаёт ровно тот же упорядоченный поток
граней компактными срезами; C F2B подаёт тот же набор пакетов/вызовов в
неубывающем порядке ближайшей AABB-глубины; ZPRE даёт depth-pass без записи
цвета/альфы, затем тот же цветной поток без записи глубины и неизменный
речной проход; в неподвижной позе нет hot vertex/index/texture uploads;
UI MIN=2 строки, замороженный результат не рендерит native. Desktop doubles
не растеризуют M3G и не измеряют телефонный FPS.
