# GRID + Z против настоящего offline BSP без Z

Отдельный просмотрщик карты: [JAR](../downloads/Quantum_StaticRoom_Bsp.jar),
[JAD](../downloads/Quantum_StaticRoom_Bsp.jad),
[build report/SHA-256](../downloads/Quantum_StaticRoom_Bsp.build-report.json).
Основная игра и все опубликованные JAR, включая Perspective ON/OFF, сохранены.
Это диагностический renderer, не полный перенос игровой логики.

## Управление и телефонный замер

- При запуске **A GRID+Z** — исходная фиксированная GRID4×4, depth ON.
- **0** переключает A↔B. **1** всегда A, **3** всегда **B BSP-Z**.
- **\*** переключает B↔**C BSP+Z**; из A сразу выбирает C.
- **5** — исходная камера/yaw0, **4/6** — поворот, **2/8** — движение,
  **7/9** — вбок, **#** — выход.

Выбрать неподвижный ракурс, снять A→B→C→B→A. После каждого переключения ждать
числового FPS и ещё одного обновления; при низкой скорости ждать дольше обычных
8секунд. Камера/viewport/Image сохраняются, ввод движения обнуляется, статистика
сбрасывается:1секунда прогрева, первый завершённый anchor-кадр, затем окно≥3секунд
и не менее2 интервалов. Пауза/hide/resize также сбрасывают прогрев.

Нужны фото **всего HUD и самой сцены**. Смотреть на перекрытия домов/дороги,
края alpha-текстур и реку. При ошибке `Failed` — выход и перезапуск, без тихого
перехода на другой renderer или пропуска геометрии.

## Зачем третий режим

**A и B не отличаются одним лишь Z.** BSP разрезает полигоны и иначе отсекает
геометрию. Его порядок ограничивает batching, поэтому вызовов может стать больше.
**B и C** используют **одни и те же resident pages, indices, порядок, culling,
камеру, текстуры и освещение**. Меняются только:

| Режим | bindTarget depth | depth test | opaque depth write | depth clear |
|---|---|---|---|---|
| A GRID+Z | ON | ON | ON | ON |
| B BSP-Z | OFF | OFF | OFF | OFF |
| C BSP+Z | ON | ON | ON | ON |

У реки depth write **OFF во всех режимах**. В B/C река стоит в общем BSP-порядке,
а не принудительно после всей комнаты; mode7/MODULATE и alpha сохранены.
B/C позволяют оценить цену depth-операций на этом конкретном painter-порядке,
но не предсказывают выигрыш от выключения Z в исходном material-order A.

## Настоящее BSP, а не сортировка центров

На компьютере экспортируется полный native triangle stream immutable Tex3:
**4750 треугольников**, включая правильную диагональ и чередование winding
исходных triangle strips. Из него строится polygon-plane BSP: пересекающие
плоскость полигоны реально разрезаются, новые XYZ/UV/baked RGB интерполируются.
Нет approximate unsorted leaves или сортировки по средней глубине.

Результат: **2815 разрезаний, 9591 треугольник, 5827 узлов, глубина68**.
Это BSP-порядок и frustum culling, **не PVS и не автоматическое отсечение за стенами**.

На телефоне готовое дерево только читается при загрузке. Каждый кадр —
консервативный subtree-AABB/frustum test и обход **far → coplanar → near**.
Сторона определяется от того же сдвинутого/квантизованного camera origin, который
передаётся в M3G, а не от несдвинутой игровой позиции. Стек обхода выделен заранее.
Near128/far60000/FOV74, полный Canvas/Image viewport, perspective ON с исходной
политикой материала, baked light/drawmode9, alpha thresholds и4 кадра реки/speed6
одинаковы для всех режимов. Fog/динамический свет/софт-fallback не добавляются.

### Буферы и вызовы

BSP хранится в **76 компактных resident pages до384 вершин**, всего28773 вершины.
Это не5827 отдельных native VertexBuffer. Порядок разбит на5852 spans; объединяются
**только соседние в painter-порядке spans одной page**. Нельзя собирать все грани
одной текстуры через промежуточную поверхность — это сломало бы перекрытия без Z.

VertexArray/UV/color/текстуры загружаются один раз. **Новая** видимость или порядок
может собрать ordered index buffers перед bindTarget; есть **двухэлементный
кэш точных последовательностей**, не hash-only совпадение. В неподвижной позе,
при анимации реки и переключении B↔C ничего из этого не пересоздаётся. У A свой
прежний двухэлементный mask cache. Внутренние загрузки драйвера этим не измеряются.

**Счётчики desktop API-теста**, не скорость телефона, камера240×320/focal212,
исходная позиция/yaw0:

| Режим | T подано | DC вызовов | VB вместимость поданных буферов |
|---|---:|---:|---:|
| A GRID+Z | 2090 | 3 | 10032 |
| B/C BSP | 1063 | 104 | 38964 |

104 вызова вместо3 могут перечеркнуть экономию геометрии/Z. **Ускорение не обещано.**
T включает треугольники после разрезания; VB не равно фактически обработанным
вершинам GPU. Разрешение телефона может дать другие счётчики. Обе структуры
резидентны в одном JAR, поэтому память выше, чем у старого отдельного Tex3;
абсолютный FPS A не обязан совпасть с прежним JAR.

### Точность новых вершин

M3G VertexArray не хранит произвольные float XYZ. Для новых BSP-вершин используются
short XYZ с локальными bias и **общей решёткой шага3** для всех pages.
Исходные XYZ сохраняются точно; только новые точки разреза округляются. Общая
решётка не даёт одинаковой точке округлиться по-разному из-за масштаба страницы.
Измеренная максимальная ошибка компоненты — **1.5 мировой единицы** (для масштаба: высота камеры над START
в этом просмотрщике1503). UV: максимум1/65536 нормализованной координаты; RGB:
до0.5 уровня из255. Alpha атрибута255, исходный texture alpha-test остаётся.

Это **не pixel-identical геометрия A**. На краях/линиях разреза возможны небольшие
расхождения; округление координат и float planes может влиять на порядок у самой
плоскости. C нужен также для визуального контроля B на той же упакованной геометрии.
Проверки математического BSP до упаковки не выдаются за проверку пикселей телефона.

## HUD

`FPS` с десятыми; `N` — вся native транзакция; `C` — Image→Canvas;
`I` — интервал кадров. `J/B/K/R/E` — подготовка/culling/cache, bind, state/clear,
render loop, release. Это coarse Java API wall time, **не GPU timestamps**.
`T/DC/VB`, `S/V/CUT` — треугольники/вызовы/вместимость VB, выбранные углы,
проверки bounds/отвергнутые subtree. В A V/CUT относятся к GRID-ячейкам;
в B/C — к узлам дерева, эти V/CUT нельзя напрямую считать одинаковой работой.

## Сборка и проверка

Обычный toolchain репозитория: ECJ4.8, Java, Java ME API, ProGuard/preverification,
подмодули Room/StringTools; `build/cldc/api.jar` — SDK union CLDC/MIDP/JSR135/
JSR184/JSR75_file для desktop harness. При отсутствии javac задать JAVA/ECJ_JAR.

```sh
# Экспорт/разрезание ТОЛЬКО на компьютере, затем CLDC JAR:
python scripts/build_static_room_bsp.py --prepare-bsp --output-dir downloads
# Без --prepare-bsp берётся проверенный versioned .bsp fixture.
python -m unittest discover -s tests/static_room_bsp -p 'test_*.py'
python tests/static_room_bsp/run.py
python tests/static_room_bsp/run.py --packaged
python -m unittest tests/resources/test_static_room_bsp.py
python scripts/verify_render_checkpoints.py
```

- Source и готовый CLDC JAR: по**2460185 assertions / 432 camera/river cases**.
  A совпадает с frozen GRID, B/C отличаются только глубиной. Полный порядок проверен
  независимым рекурсивным обходом, включая actual shifted eye, page/indices и winding.
- Проверены отсутствие hot vertex/texture uploads и stationary index rebuild,
  B/C reuse, bind/clear/render/release failures, реальный UI→renderer, freeze/hide,
  прогрев/часы;16 испорченных/truncated assets отвергаются без fallback.
- Offline4 tests: каждый исходный треугольник сохраняет площадь/ориентацию,
  новые атрибуты проверены независимыми barycentrics, ancestry всех разрезаний;
  проверена точная представимость всех исходных XYZ общей решёткой;
  независимый oracle **512 rays / 3043 пересечения** проверяет покрытие и painter
  порядок **до quantization**. Детерминированное повторное построение даёт те же bytes.
- 195 CLDC47.0 classes/1225 StackMap attributes. Все182 baseline classes и все
  прежние assets сохранены побайтно; добавлены13 классов и один BSP asset.
- Детерминированные export/convert/JAR/JAD/report проверены побайтно.
  StaticRoom/PolyFill/Software/L2D resource-аудиты:28 PASS;7 rollback checkpoints PASS.

Doubles не растеризуют native M3G и не измеряют E65. Телефонных результатов BSP
