# M3G: найденные источники лишней работы — 18.10.2026

## Вывод

На настоящей геометрии из пользовательского архива воспроизведены:

1. **Дробление Fog-пакетов по масштабу координат**, даже с одной текстурой
   и одинаковым материалом. Это подтверждённый источник избыточных draw-вызовов
   в режиме 6; тот же механизм используется в режиме 3.
2. **Переходы на CPU из-за отказа упаковки отдельных полигонов**:
   вершины за камерой и ограничения точности homogeneous weight. Они вызывают
   чтение полного кадра, а при продолжении M3G — обратную загрузку.

Это не измерение времени GPU и не доказательство, что именно эти операции
занимают большую часть времени на телефоне. Узкое место **по FPS конкретного
пользовательского кадра D:119 пока не установлено**: точная локация, координаты,
настройки, NPC и исполнение J2ME Loader в этом тесте не воспроизведены.

**Рабочий движок и ресурсы не изменены.** Изменения этого исследования — только
опциональный тестовый зонд и документация. Fog в игре не отключён.

## Методика и ограничения

Источник: `q 92 20251201y.jar.zip`, SHA-256
`b6be7a932ef45c12a3ac97d8d588f4875ecaf679392dc5342444622983a2f956`.
Движок соответствует опубликованной BLEND-сборке; подготовка ресурсов описана
в [game-resource-tests.md](game-resource-tests.md).

`WorldBottleneckProbe` использует:

- настоящий приватный декодер `Room.createFrom3d` через reflection, с передачей
  потока из тестового classpath, без модификации формата или кода декодера;
- настоящие PNG-атласы, декодированные ImageIO только в настольном тесте;
- `WORLD_SCALE`, `DMODE`, `FOGD`, `DIST`, `FLOOR_OFFSETSZ` из конфигов;
- обычную загрузочную оптимизацию `Mesh.optimize()` по
  `OPTIMIZE_LEVEL_MODEL` (по умолчанию включена);
- настоящие transform/project, isVisible, applySz, сортировку очереди и адаптер;
- инструментированные M3G API doubles: считаются вызовы, а не время GPU.

Последняя mesh многокомнатного файла — описание порталов, как в `HouseCreator`;
она **не подаётся как геометрия мира**. Но все остальные комнаты подаются
намеренно: без обхода порталов House и без chunk-culling. Поэтому этот зонд —
**изолированный анализ подачи мировой геометрии**, а не точная игровая сцена.
Не загружаются NPC, предметы, анимации, сохранения, lightmap-файл и gameplay.
Lighted-полигоны имеют исходные цвета конструктора; оценка картинки не проводится.

Разрешение 240×320; `pixelsQ=2`, `persQ=4`, `fogQ=2`, mipmapping выключен.
Камера: START из конфига + 1503 по Y; yaw 0/90/180/270, pitch 0/60.
После прогрева второй кадр каждого ракурса считается отдельно, без HUD-пиков.
Фон — один полноэкранный SolidSky, **не настоящая панорама**; он добавляет
один draw. Дождь и постэффекты отсутствуют. Это исключает барьер частичного
неба: зарегистрированные ниже readback связаны с мировой геометрией.

Для диагностики `run.py` создаёт временные копии трёх классов:
`M3GSceneRenderer`, `M3GPolygonBatch`, `ProjectedGeometry`.
В них добавлены только счётчики причин flush/отказов. Исходники `src/` не
редактируются, условия и возвращаемые значения не меняются. Эти копии и тестовые
классы никогда не включаются в игровой JAR. Полный набор контрактов проходит
и с инструментированными копиями, и без них.

## 1. Fog: общий двоичный шаг всё ещё не общий для пакета

`ProjectedGeometry.packFog` выбирает `shift` и `scale = 2^shift / distance`
**для каждого полигона отдельно**, исходя из экранных координат и глубины.
`M3GPolygonBatch.add` принудительно завершает пакет, если
`fogged && this.scale != scale`.

Таким образом, сохранение одной текстуры/Fog/материала не гарантирует объединение
соседних полигонов. Различные двоичные шаги тоже дают разные scale.

Реальная карта уровня 40: 4 mesh-комнаты, 1988 вершин после оптимизации,
1710 полигонов, атлас 256×256, режим 6.

| yaw / pitch | Полигонов в очереди | D | B | T | Разрывы по Fog-scale | По текстуре / прочему состоянию |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 0 / 0 | 31 | 19 | 1 | 0 | 17 | 0 / 0 |
| 270 / 0 | 49 | 21 | 1 | 0 | 19 | 0 / 0 |

При yaw=0 все 29 принятых нативно полигонов использовали двоичную Fog-упаковку;
отката к старому индивидуальному упаковщику не было. Следовательно, проблема
не сводится только к legacy fallback: **сама двоичная сетка выбирается локально**.
При yaw=270 двоичная упаковка сработала 47 раз, старый упаковщик — один раз.

Контрольный эксперимент: те же координаты, та же очередь и геометрия, но
у тестового объекта Texture режим 6 заменён на 0. Файлы не редактируются,
это **не рекомендуемое изменение внешнего вида игры**.

| yaw / pitch | D с Fog | D без Fog в эксперименте | B до / после |
| --- | ---: | ---: | --- |
| 0 / 0 | 19 | 2 | 1 / 1 |
| 270 / 0 | 21 | 3 | 1 / 1 |

Это подтверждает источник разбиения, но **не означает ускорение FPS в 7–9 раз**:
стоимость пикселей, CPU, GPU и синхронизации не измерена.

Направление исправления: согласовать допустимый масштаб внутри упорядоченного
Fog-пакета, а не просто увеличить ёмкость или выключить Fog. Обязательны проверки
точности глубины, общих рёбер и сохранения painter-order. Для 9/13 эта причина
не действует: native distance Fog из них уже удалён.

## 2. Малое число полигонов может вызвать дорогие CPU-переходы

В `ProjectedGeometry.pack` вершина с `rz > 0` немедленно возвращает 0;
в Fog-пути такое же условие есть в `packFog`. Для принятой isVisible грани
достаточно, чтобы не все вершины были за камерой: пересекающая камеру грань
может остаться в очереди, но затем не пройти нативную упаковку.

Вторая подтверждённая причина — условие ограничения точности q:
`q <= 0 || q > 32767 || abs(q * scale - w) > w / 128`.

`M3GSceneRenderer.draw` возвращает false, после чего `DirectX7.drawRenderObject`
вызывает barrier и настоящий CPU-растеризатор. Продолжение M3G может снова
копировать CPU-буфер в Image. При этом надпись M3G остаётся: это смешанный
кадр, а не обязательно полное отключение backend.

Пример уровня 27, yaw=0/pitch=60 после обычной оптимизации mesh:

- 3 mesh-комнаты, 3059 вершин, 2318 полигонов в исходной мировой геометрии;
- в очередь попало только **9 полигонов**;
- **3 отказа упаковки**: два из-за вершины за камерой, один из-за точности q;
- **D:4 / B:2 / T:0**;
- **2 вызова Image.getRGB и 2 вызова Graphics.drawRGB за кадр**.

При 240×320 каждый такой вызов обрабатывает полный массив 76800 пикселей,
а не только прямоугольник отказавшего полигона. T:0 здесь означает отсутствие
загрузок текстур, **но не отсутствие обратных загрузок framebuffer**.

В уровне 19, yaw=180/pitch=0, аналогично: 18 полигонов в очереди,
3 отказа упаковки, D:3/B:2/T:0, два readback и одна обратная загрузка.

Направление исправления: расширить нативный путь для пересекающих камеру граней
и/или надёжно обрабатывать диапазон упаковки, не выбрасывая видимые полигоны.
Нельзя просто удалить fallback или ослабить точность без проверки картинки,
Fog, интерполяции UV и атомарного восстановления после ошибки.

## 3. Что не подтверждено как главная причина

- Дождь из 16 частиц — один draw; отдельные ресурсные тесты пяти панорам с
  дождём дали максимум D:2–3 на выбранных ракурсах. Это не объяснение D:119.
- В приведённых прогретых опытах T=0: повторные загрузки текстур отсутствуют.
  Это не исключает нехватку кеша при большем количестве NPC/анимаций в игре.
- В M3G сохраняются CPU transform/project и сортировка выбранной геометрии.
  Это потенциальная CPU-нагрузка, но число трансформируемых вершин в этом зонде
  нельзя считать числом вершин пользовательского кадра: House/chunks здесь
  обходятся намеренно.
- Отдельный ожидаемый B:1 при частичной панораме отличается от описанных
  CPU-отказов мировой геометрии. Общий HUD-счётчик их не различает.

Для окончательного ранжирования по FPS нужен профиль той же сцены в настоящем
J2ME Loader: время подготовки мира/NPC, упаковки/отправки, readback/upload и
presentation. По одному числу D отличить эти затраты нельзя.

## Повторить

Сначала обычная CLDC-сборка и `python scripts/game_resources.py`, затем:

```sh
QUANTUM_RESOURCE_JAR="$PWD/build/game-resources/resources.jar" \
QUANTUM_WORLD_PROBE=1 \
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar \
python tests/m3g/run.py > build/game-resources/world-probe.log 2>&1
```

В логе строки `PROBE`: причины отказов, разрывов пакетов, настоящие
framebuffer-copy счётчики и число отправленных полигонов. Одновременно проходят
**147 PASS-групп** (140 исходных, 6 ресурсных, 1 диагностическая).
Без `QUANTUM_WORLD_PROBE` временная инструментализация не включается.

Практический следующий шаг — отдельная [сборка с таймерами полного кадра](m3g-frame-profile.md),
которую нужно запустить в той же сцене на устройстве пользователя.
