# M3G CHUNK_SIZE 60000 / 40000

Отдельный MIDlet: [JAR](../downloads/Quantum_StaticRoom_Chunks.jar),
[JAD](../downloads/Quantum_StaticRoom_Chunks.jad),
[build report и SHA-256](../downloads/Quantum_StaticRoom_Chunks.build-report.json).
Tex3, Packets, Layouts и основной игровой renderer не заменены.

## Телефонный замер

1. При запуске **CHUNK 60000**. **5** — исходная камера. Не двигаться, дождаться
   числового FPS и ещё одного обновления (обычно8секунд), фото всего HUD.
2. **0 → CHUNK 40000**: та же поза, тот же срок, второе фото.
3. **0 → CHUNK 60000**: контрольный повтор.
4. По желанию **1 → GRID4x4**, старая фиксированная сетка в том же JAR.
   **0** из контроля возвращает60000; **3** всегда выбирает40000.

**4/6** поворот, **2/8** вперёд/назад, **7/9** вбок, **5** исходная поза/yaw0,
**#** выход. При переключении ввод движения обнуляется, поза и Image target
сохраняются, окно измерения сбрасывается. При ошибке явное сообщение и выход,
нет тихого fallback с другим объёмом геометрии.

## Что именно подключено

Значения60000 и40000 теперь реально задают ширину X/Z-ячейки **в мировых единицах
после WORLD_SCALE**, а не просто записаны в неиспользуемый параметр конфига.
Обе сетки строятся при загрузке, начало общее для всех материалов — minX/minZ
комнаты. Занятые ячейки хранятся разреженно. Грань назначается по центру своего
AABB; **в проверку идёт полный AABB всех граней ячейки**, а не квадрат60000/40000.
Поэтому длинные/пересекающие границы грани не обрезаются и не теряются.

Это безопасная версия пространственного отсечения для статического M3G:
проверяем все занятые ячейки по frustum. **Не копируем старое ограничение
Room.render до3×3 соседних ячеек**, которое при малом CHUNK_SIZE могло бы
скрывать ещё видимую геометрию. Значение0 здесь — только диагностический контроль
GRID4x4, не переопределение смысла CHUNK_SIZE=0 в основном движке.

Дальность **far60000**, near128, FOV74, полное разрешение Canvas/Image, alpha ON,
исходные XYZ/UV/baked RGBA, текстуры и все4 кадра реки/speed6/mode7 прежние.
Крупные VertexBuffer прежние, индексы оставшихся граней собираются в **исходном
порядке** по родительским буферам, не рисуем каждую ячейку отдельным call.
Компактные/SHARED профили Layouts сюда не примешаны.

В прогретой неподвижной позе: проверки AABB ячеек, без построения/upload геометрии.
Если видимость ячеек не изменилась, не пересчитывается даже список выбранных
граней. При новом наборе — прежний двухэлементный кэш index buffers. Он позволяет
прогретое60000↔40000 без новых индексов; третий контроль/движение могут вытеснить
маску. Это не постоянная пересборка каждый кадр.

## HUD / ожидания

- FPS дробный:1с прогрев, completed-frame anchor, затем≥3с окна, минимум2 кадра.
- N — native render path; C — LCDUI.drawImage; I — frame interval (N входит в I).
- T — выбранные треугольники, S — углы; V — проверенные занятые ячейки;
  CUT — отвергнутые ячейки.
- DC — вызовы Graphics3D.render. VB — сумма ёмкостей на вызов, **не аппаратный
  счётчик обработанных вершин**. При нескольких размерах сетки VB может оставаться
  одинаковым: здесь меняем отбор индексов, не сами vertex buffers.
- J/B/K/R/E — средние ms prepare/bind/state+clear/render/release. Coarse API wall
  time, **не GPU timers**. Release может ждать отложенную работу, не только копию.

Меньшая ячейка не обязана ускорить: больше проверок, другое объединение AABB,
меньше лишних граней — возможен любой баланс.40000 и60000 не вложенные сетки,
поэтому строгая монотонность T не обещается. И старая4×4 может оказаться лучше.

**Контроль состава кадра на desktop doubles, не телефонный результат:**
240×320/focal212, pose(-77706,-1209,-103802), yaw/pitch0:

| Сетка | T | DC | VB | V | CUT |
|---|---:|---:|---:|---:|---:|
| GRID4x4 | 2090 | 3 | 10032 | 33 | 28 |
| 60000 | 2628 | 3 | 10032 | 22 | 17 |
| 40000 | 2607 | 3 | 10032 | 40 | 33 |

В этой конкретной позе новая сетка **не уменьшила T относительно старой**.
Это не предсказывает FPS/картинку E65. Нужен замер в одном JAR и одной позе.

## Проверки и воспроизведение

Source и packaged CLDC JAR:1728 комбинаций60000/40000 (3 позиции ×3 pitch ×24 yaw
×4 river frames ×2 размера), плюс864 сравнения GRID4x4 с immutable Tex3.
Независимый oracle строит группы/AABB из захваченных packed native attributes;
проверены точные индексы/strip order, сохранение индивидуально потенциально
видимых граней, native state/проекция/текстуры/река. Boundary/отрицательные
координаты/длинные пересекающие грани, warm cache и отсутствие vertex/texture
uploads, OOM-before-bind без fallback, target release при ошибках, клавиши/поза,
скрытая Canvas и часы. **Doubles не растеризуют и не измеряют FPS телефона.**

Все182 класса/все assets Tex3, кроме manifest, побайтно сохранены. Только9 новых
классов и отдельное имя MIDlet. SHA исходников/скрипта/родителя, class47.0,
preverify/StackMaps, JAD/размер и архив аудируются отдельно.
