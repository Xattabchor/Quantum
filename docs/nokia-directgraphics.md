# Вывод через Nokia DirectGraphics

## Что переведено

`DirectX7.flush()` и пиксельные фоны паузы, настроек, настройки клавиш и
меню разработчика используют общий `PixelBlitter`. На устройствах с Nokia UI API
он вызывает `DirectUtils.getDirectGraphics(g).drawPixels(...)` с форматом
`TYPE_INT_8888_ARGB` и без поворота/отражения. Полученный DirectGraphics относится
к текущему Graphics: его трансляция и clipping не заменяются состоянием другого
кадра или изображения.

При отсутствии API/адаптера используется MIDP `Graphics.drawRGB`. Nokia-классы
изолированы в `NokiaPixelBlitter`, загружаемом по имени. Проверка при первом
рисовании также обрабатывает отложенное разрешение отсутствующего API.
Если `getDirectGraphics` возвращает `null`, резервный вывод применяется только
к этому вызову. Ошибки данных и нехватка памяти не подавляются.

## Ограничение API

**Это переход вывода кадра на DirectGraphics, а не аппаратный 3D-рендерер.**
Nokia DirectGraphics предоставляет операции с пикселями и плоскими цветными
примитивами, но не имеет текстурированных треугольников с UV, перспективной
интерполяцией и глубиной. Поэтому растеризация сцены по-прежнему программная.
Замена её на `fillTriangle` потеряла бы текстуры, освещение и эффекты оригинала.
Для аппаратной растеризации нужен другой API, например M3G/JSR-184.
Ускорение от `drawPixels` зависит от устройства/эмулятора и здесь не измерялось.

## Совместимость файлов и эффектов

Загрузчики моделей, текстур (включая QCT), уровней и конфигурации не изменены.
Не требуется конвертация оригинальных ресурсов, изменение путей или упаковки.
Также сохранены:

- публичный интерфейс `DirectX7`, в том числе `int[] display` и `getDisplay()`;
- сортировка полигонов, порталы, UV, mipmapping и режимы материалов;
- постобработка кадра, снимок фона паузы и отладочная карта перерисовки;
- `flushAlpha`: при `false` старший байт игнорируется, при `true` используется
  исходный ARGB; принудительная установка альфа-канала не производится;
- исходные offset, scanlength, координаты и размеры пиксельного блока.

Адаптер не создаёт второй кадровый буфер, не преобразует цвет в RGB565 и не
меняет содержимое переданного массива.

## Сборка

Нужны существующие инструменты проекта: NetBeans Mobility/Java ME SDK,
CLDC 1.1, MIDP 2.0 (или 2.1), необходимые JSR и библиотеки из подмодулей.
Дополнительно нужен Nokia UI API jar из установленного SDK. Его реализации
нельзя включать в MIDlet: API предоставляет устройство или эмулятор.

1. Инициализируйте зависимости: `git submodule update --init --recursive`.
2. Настройте Java ME platform в NetBeans для установленного SDK.
3. Укажите путь к Nokia API jar в `nokia.ui.classpath` (например, в локальном
   `nbproject/private/private.properties`) или передайте Ant-параметр:

   ```sh
   ant -Dnokia.ui.classpath=/path/to/sdk/lib/nokiaui.jar jar
   ```

   Название jar зависит от SDK. Если Nokia API уже входит в bootclasspath
   выбранной платформы, дополнительный jar не требуется.
4. Добавьте оригинальные игровые ресурсы в `res/` с исходными путями.

Свойство подключено к compile classpath и к `extra.classpath` для preverify и
исключения SDK-классов из `Quantum.jar`. Не используйте jar с реализацией
эмулятора вместо API jar. Не копируйте тестовые заглушки в `src/` или `res/`.

В проекте обфускация сейчас выключена. При её включении нужно сохранить имя и
конструктор класса, загружаемого через `Class.forName`. Пример правила ProGuard
(добавьте в используемый custom obfuscation script):

```text
-keep class code.Rendering.NokiaPixelBlitter { public *; }
```

## Проверки

На обычном JDK с Python 3:

```sh
python3 tests/pixel_blitter/run.py
```

Можно указать `JAVA`/`JAVAC` или `JAVA`/`ECJ_JAR` для Eclipse batch compiler.
Тесты компилируют только адаптер и тестовые API-заглушки во временный каталог.
Проверяются выбор DirectGraphics, отсутствие лишнего MIDP-вызова, передача
массива без копирования/изменения, параметры и альфа, положительный и отрицательный
scanlength, трансляция/clipping в модели Graphics, смена контекста, `null`-wrapper,
отсутствие Nokia API и адаптера в runtime, отложенный NoClassDefFoundError и
распространение OutOfMemoryError. Это контрактные тесты, а не проверка реализации
Nokia на реальном телефоне.

Автономная сборка и preverify выполнены через ECJ 3.16.0 и ProGuard 6.2.2
с настоящими Java ME API jar (не тестовыми заглушками). В первой сборке DirectGraphics получены 126 классов
версии 47.0 и 879 CLDC StackMap-атрибутов; актуальные числа записываются
в `artifacts/build-report.json`. Проверка на устройстве не выполнялась.
Игровых ресурсов в checkout нет: собранный JAR содержит движок, но без них игра
не запустится. На устройстве/эмуляторе нужно отдельно проверить сцену,
прозрачность, эффекты урона/виньетку, фон паузы, изменение размера области 3D
и отладочную карту перерисовки.

## Автономная сборка preverified JAR

Без NetBeans можно использовать Python 3.8+ и скрипт:

```sh
python3 scripts/build_cldc.py \
  --java /path/to/java \
  --ecj-jar /path/to/ecj.jar \
  --api-dir /path/to/j2me/lib \
  --proguard-jar /path/to/proguard.jar
```

Использованный ECJ 3.16.0 находится в npm-пакете `coc-java@1.0.0`
(`server/plugins/org.eclipse.jdt.core_3.16.0.v20181004-1305.jar`).
API jar и ProGuard 6.2.2 взяты из
[выкладки Java ME build tools](https://github.com/vipaoL/j2me-build-tools).
Их нужно получить отдельно; скрипт ничего не скачивает.
В `--api-dir` ожидаются `cldc11.jar`, `midp21.jar`, `nokiaui.jar`,
`jsr135.jar`, `jsr184.jar`, `jsr75_file.jar`.

Скрипт компилирует все исходники и подмодули с `-source 1.3 -target 1.3`
против Java ME API, запускает ProGuard с `-microedition` **без** обфускации,
оптимизации и удаления классов, затем проверяет версию class-файлов,
наличие CLDC `StackMap` и отсутствие Java SE `StackMapTable`.
Проверка структуры не заменяет тестирование на телефоне.

Результаты в `artifacts/`: `Quantum.jar`, `Quantum.jad`, `build-report.json`.
Промежуточные файлы и логи — в `build/cldc/`. Эти каталоги не добавляются в Git.
`res/README.md` не включается; остальные файлы из `res/` упаковываются
с исходными путями. Если ресурсов нет, JAR всё равно собирается, но отчёт
явно указывает `resource_files: 0`. JAD указывает размер готового JAR,
а отчёт содержит SHA-256 и результаты структурной проверки.
