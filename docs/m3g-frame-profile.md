# Диагностика ограничителя FPS на устройстве

## Статус

Предыдущий [анализ геометрии](m3g-bottleneck-analysis.md) доказал разрывы
Fog-пакетов и CPU-fallback, но **не установил доминирующую по времени операцию
пользовательского кадра**. Для этого нужен замер в том же J2ME Loader/телефоне,
а не время инструментированных API doubles на сервере.

Добавлена отдельная диагностическая сборка **Quantum Profile** с wall-clock
таймером этапов. Она не оптимизирует рендер, не выключает Fog, не меняет отбор
геометрии, ресурсы, gameplay или порядок отрисовки. Основные `src/` и
опубликованный `downloads/Quantum.jar` не изменены.

Здесь выполнены сборка, preverification и контрактные тесты. **Запуск в Android
J2ME Loader, измерение его FPS и окончательное определение ограничителя FPS ещё
не выполнены.** Показания следует получить от пользователя на его устройстве.

## Что сделать пользователю

1. Запустить диагностический JAR. Полный тестовый пакет построен на ресурсах
   `q 92 20251201y.jar.zip`; их конфиги, доступность уровней и сохранения не
   переписываются. Название MIDlet — Quantum Profile, чтобы отличать его от
   обычной сборки. Настройки нового MIDlet могут отличаться из-за другого RMS.
2. Выбрать **M3G** и выставить те же разрешение, качество, Fog, HW perspective,
   mipmapping, ограничение FPS и параметры J2ME Loader, что в исходном замере.
3. Перейти **в ту же локацию, к той же позиции и направлению камеры**, где
   наблюдались низкий FPS и D:119. Стоять неподвижно минимум пять секунд после
   загрузки и сделать скриншот строк `PF` и `TOP`.
4. Если этот архив ресурсов отличается от игрового пакета Stalkere со
   скриншота или не даёт попасть в нужную локацию, нужен именно тот игровой JAR
   для установки диагностических классов с сохранением его ресурсов.
   Профиль другой локации не докажет причину исходного кадра.

Диагностический HUD появляется в M3G независимо от `showFps`. Старые D/B/T
показываются как раньше, если включён `showFps`. Он занимает верхнюю часть
экрана LCDUI **после** завершения основного кадра, поэтому не уменьшает
отрисовываемую геометрию или пиксели сцены.

## Как читать

Все числа — **средние миллисекунды на кадр за окно примерно одну секунду**,
а не проценты и не максимумы. Например, 16 FPS соответствуют интервалу около
62,5 мс, но не доказывают, какая часть интервала занята движком.

Строка `PF L1 n16 I62.5 F60.0 G2.5` означает:

- `L1` — номер уровня, `n16` — число завершённых выборок;
- `I` — интервал между началами соседних вызовов paint;
- `F` — время внутри измеренного paint + синхронного run, включая явный sleep;
- `G` — промежуток между концом измеренного кадра и началом следующего paint.

Выборки парные: предыдущий завершённый кадр учитывается при начале следующего.
Поэтому **I = F + G**, с погрешностью отображаемого округления.

| Поле | Измеряемый участок |
| --- | --- |
| P | `House.getParts` и `Scene.render`: подготовка сцены без выделенного отдельно V |
| V | Два `DirectX7.transformAndProjectVertices`: CPU-преобразование и проекция вершин |
| M | `ProjectedGeometry.pack/packFog`: CPU-упаковка координат, включая float/long арифметику |
| S | Остальная работа `renderGameFrameImage`: подготовка погоды, обход/подготовка материалов, данные VertexArray и вызовы установки состояния; не только чистая Java-арифметика |
| Z | Сортировка world/background очередей |
| A | Wall-clock внутри `Graphics3D.render`, bindTarget, releaseTarget, clear, создания Image2D |
| R | `Image.getRGB` для материализации предыдущего кадра и промежуточного M3G → CPU перехода |
| U | `drawRGB` из CPU-буфера обратно в M3G Image |
| K | Копия framebuffer в backup и обратное восстановление после ошибки |
| X | `Scene.flush`: финальная подача Image/RGB на LCDUI Graphics |
| C | Настоящий CPU-растеризатор при fallback (`drawSoftwareObject`) |
| H | LCDUI-погода, оружие, HUD, отладочные подписи и сам профилирующий overlay |
| L | Остальная игровая логика `run`, кроме отдельно выделенных E/Q/W |
| E | `Scene.update`: AI, объекты, физика и прочая работа этого метода |
| Q | `Scene.activateObject(false, ...)` внутри run: поиск активируемых объектов/соответствующие проверки |
| W | Явные `Thread.sleep` игрового цикла и паузы сообщения |
| O | Остальная настройка paint/камеры/погоды, не вошедшая в перечисленные категории |

Категории **исключающие, а не вложенные суммы**. Например, A/R/C/M/Z не
прибавляются второй раз к S, V не считается повторно в P, W/E/Q — в L.
Сумма всех категорий равна F до округления. Пример синтетических чисел выше
только объясняет формат; это не результат запуска игры на устройстве.

`TOP PACK 12.0ms` — самый большой отдельный измеренный участок. Если G больше
любого участка, выводится `TOP OUTSIDE ...ms`. Это подсказка по доминирующей
**корзине времени**, а не безусловный вердикт «виноват GPU/CPU».

## Что позволит различить профиль

- Большие **M/V**: именно CPU-упаковка или проекция, а не стоимость дождевых draw.
- Большой **C**: существенная фактическая растеризация на CPU даже при надписи M3G.
- Большие **R/U**: операция переноса полного framebuffer/синхронизации занимает время.
  R может включать ожидание GPU, а не только копирование памяти.
- Большой **A**: время в указанных M3G API. Это включает Java/native/driver и
  возможное ожидание, **не чистое время выполнения GPU**.
- Большие **E/Q/L**: ограничение может быть в логике/AI/активации объектов;
  сокращение draw-вызовов не обязательно устранит его.
- Большие **X/H**: подача на LCDUI, 2D-оружие/HUD/прочие оверлеи.
- Большие **W/G**: явная задержка или время вне измеренной работы. Для G нужны
  проверки frame pacing, лимитов эмулятора, очереди UI/планировщика, GC и
  асинхронного отображения. G нельзя автоматически назвать «простоем CPU».
- Большой **S**: оставшаяся подготовка и state/VertexArray API требуют следующего
  более узкого замера; его нельзя автоматически приравнять к чистой CPU-арифметике.

Wall-clock также включает задержки планировщика и GC, случившиеся внутри
текущего участка: это не чистое процессорное время метода. Желательны несколько
стабильных окон измерения.

В асинхронной графике фактическая работа GPU может выполняться после возврата
API. Этот таймер не заменяет аппаратный GPU profiler. Даже очень высокий TOP
одного этапа не доказывает универсальное узкое место для других сцен.

Таймер `System.currentTimeMillis` имеет ограниченную точность: 0.0 не означает
отсутствия работы. Сами таймеры на native-вызовах и overlay добавляют нагрузку;
после исправления нужно перепроверить FPS обычной сборкой без диагностики.
Явные start/stop/openPause и смена уровня сбрасывают окно. Долгие задержки вне
кадра **не отбрасываются** по произвольному порогу. Кадры со скачком часов назад
и незавершённые кадры не публикуются.

## Сборка и проверка

К обычной команде `scripts/build_cldc.py` добавить:

```sh
--profile-frame --output-dir artifacts/frame-profile/engine
```

Для полного пакета добавить также:

```sh
--resource-archive 'q 92 20251201y.jar.zip'
--output-dir artifacts/frame-profile/game
```

Скрипт создаёт **временные копии** GameScreen, DirectX7, M3GSceneRenderer и
ProjectedGeometry под `build/cldc/frame-profile-src`, плюс диагностический
`FrameProfile.java`. Обычная сборка не включает этот класс и не вызывает таймеры.
Новый флаг записан в build-report. Артефакты лежат в игнорируемом `artifacts/`,
а не в production downloads; дополнительные мегабайты ресурсов в Git не
дублируются.

Проверки генератора и арифметики профиля:

```sh
python -m unittest discover -s tests/resources -v
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar python tests/frame_profile/run.py
```

Java-тест заменяет часы **только в своей временной копии** детерминированными.
Проверены вложенность, отсутствие двойного учёта, I=F+G на парных выборках,
усреднение, TOP, длинные внешние задержки, исключения, сбросы и скачок часов.

После диагностической CLDC-сборки:

```sh
QUANTUM_FRAME_PROFILE=1 \
QUANTUM_RESOURCE_JAR="$PWD/build/game-resources/resources.jar" \
JAVA=/path/to/java ECJ_JAR=/path/to/ecj.jar python tests/m3g/run.py
```

Включаются профилированные adapter/packing-копии. Помимо обычного набора,
четыре имеющихся контракта запускаются с **активным** профайлером:
FrameTransactionTest, ImagePresentationTest, CombinedPassTest, Mode5BlendTest.
Проверяются восстановление после ошибок, владение Image, смешанные CPU/native
кадры и BLEND без изменения результатов. Флаги временных причин world-probe и
frame-profile намеренно не совмещаются в одном контрактном запуске.
