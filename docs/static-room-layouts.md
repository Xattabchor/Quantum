# Static Room Layouts — контролируемая организация данных M3G

Отдельная диагностическая сборка. Ничего не переносит в основной renderer до
замера на телефоне. Все режимы подают **одни и те же упорядоченные грани**, UV,
baked RGBA и состояния. Камера/разрешение/alpha/река/near128/far60000/FOV74 прежние.
Вершины готовятся при загрузке, индексы видимости — только при промахе кэша.
Проверяем **использование готовых данных**, не постоянную пересборку геометрии.

## Две пары для сравнения

| Режим | Данные | Число вызовов |
|---|---|---|
| **A LARGE** | Прежние крупные буферы | Прежнее |
| **B LARGE/SPLIT** | Те же крупные буферы, вызовы разбиты по пакетам C | **Как у C** |
| **C COMPACT512** | Компактные пространственные пакеты предыдущего опыта | **Как у B** |
| **D SHARED** | Точные общие вершины вместо дублирования одинаковых атрибутов | **Как у A** |

**A ↔ D** — практический тест разделяемых вершин без дополнительных calls.
Резидентный набор D: **8790 вместо10032 вершин** (−1242, около12.4%). Это не
обещание +12.4% FPS: CPU, закраска, индексы, вывод и драйвер могут ограничивать
кадр независимо от размера буфера.

**B ↔ C** — контроль ёмкости буфера при одинаковых calls/strip batches. B специально
неоптимален: несколько раз передаёт исходный большой VertexBuffer, но каждый раз
с индексами только соответствующего пакета. C передаёт маленькие срезы с локальными
индексами. Если C быстрее B — организация данных имеет наблюдаемую стоимость.
Это всё ещё не доказывает обработку ВСЕХ вершин: драйвер может по-разному выбирать
представление индексов, кэшировать трансформации, копировать/проверять буферы.

Прямое сравнение A/C остаётся tradeoff меньше capacity / больше calls. В старой
сборке Packets режим **B COMPACT512 соответствует новой C**, а не новой B.

## Что нажимать

**Сначала достаточно двух фото A и D:**

1. **5** — исходная точка и yaw0, **1** — A.
2. Не двигаться. Дождаться числового FPS вместо `warming`, затем ещё одного
   обновления (обычно достаточно8секунд). Снять фото A со всеми строками.
3. **3** — сразу D. Подождать так же, снять фото D.
4. **1** — снова A, контрольный повтор. Камера при смене режима не двигается.

Затем при необходимости B/C: из A нажать **0 → B**, дождаться чисел, снять фото;
**0 → C**, повторить. **B может быть намного медленнее**, ожидание чисел дольше
обычных8секунд: он намеренно передаёт большие буферы многократно. Это контроль,
а не рекомендуемый игровой режим. **1** всегда возвращает в A.

**0** циклически A/B/C/D, пропуская недоступные; **1** A; **3** D; **5** исходная
точка; **4/6** поворот; **2/8** вперёд/назад; **7/9** вбок; **#** выход.
При смене режима ввод движения обнуляется, но поза сохраняется. После движения
остановиться и дождаться нового полного окна. Закрыть остальные MIDlets;
сравнивать в одном запуске при одинаковых условиях A/D/A и B/C/B.

## Показатели

- **FPS**: завершённые paint-проходы / steady wall time, включая Image/LCDUI/HUD,
  GC и планировщик. Прогрев1с, затем не менее3с; первый кадр задаёт границу окна.
- **N**: весь nativeRoom.render, включая Java selection/prep и release.
- **C**: LCDUI.drawImage; **I**: интервал между началами кадров. N входит в I.
- **T**: треугольники; **S**: углы выбранных граней. Должны совпадать во всех
  режимах при одной неподвижной камере.
- **DC**: Java-вызовы Graphics3D.render; должно совпадать A/D и B/C.
- **VB**: сумма ёмкостей переданных буферов **на каждый вызов**. В B один и тот же
  большой буфер считается повторно. Не уникальные вершины и **не аппаратный
  счётчик обработанных вершин**.
- **RES**: резидентные вершины A+C+D, обычно28854; B использует буферы A.
- **AV ABCD**: доступные режимы; `A--D` означает отключённые B/C, `A---` — только A.

### Разбивка N: строка J/B/K/R/E

Все значения — средние целые миллисекунды одного окна:

- **J** — подготовка внутри renderer: frame image lookup, camera matrix,
  visibility и выбор/кэш индексов;
- **B** — bindTarget;
- **K** — viewport/camera/state, resetLights и color/depth clear;
- **R** — цикл вызовов Graphics3D.render;
- **E** — releaseTarget.

Это **API wall time, не GPU timestamps**. Асинхронный драйвер может вернуть
render быстро, а ожидать завершение при release. Большое E не доказывает чистую
стоимость копирования; там может ждать предыдущая работа. K включает не только
clear. Из-за дискретности часов, округления средних и накладных расходов сумма
не обязана в точности равняться N. Ноль не означает отсутствие работы.
Таймеров лишь несколько на кадр, одинаково для всех режимов; timestamp overhead
тоже входит в опыт. Вершины/текстуры они не перезагружают.

## Точность, кэш и память

D хэширует **точный packed tuple**: signed-short XYZ + short UV + byte RGBA, только
внутри одного исходного родительского буфера/совместимого material state.
Коллизии разрешаются полным сравнением tuple, а не одним hash. Используется
первое вхождение; UV-швы и разные baked-цвета не сливаются. Нет epsilon, новой
квантизации, сортировки граней, изменения диагонали quad или scale/bias.
Нормалей/динамического lighting в этом static пути нет.

A строится полностью первым. Затем один раз D и C; текстуры общие, не дублируются.
CPU staging arrays отпускаются. Сохраняется old→shared index map для новых масок.
Двухэлементный кэш видимости прежний. Пары глобальных B / локальных C индексных
списков строятся вместе; D индексы — лениво. Прогретый цикл всех четырёх режимов
в одной позе не создаёт новые VertexArray/Image2D/индексные буферы.

Контроль **только состава кадра на desktop doubles, не телефонной скорости**:
viewport240×320/focal212, pose(-77706,-1209,-103802), yaw/pitch0:

| Режим | T | DC | VB |
|---|---:|---:|---:|
| A | 2090 | 3 | 10032 |
| B | 2090 | 26 | 216180 |
| C | 2090 | 26 | 6409 |
| D | 2090 | 3 | 8790 |

OOM опционального D не отключает C/B; OOM C отключает B/C, но сохраняет D/A.
Во время render/подготовки маски сбой не подменяет layout или видимость молча;
target освобождается через finally, ошибка видна, **1** возвращает в A.
Нет CPU fallback и клавиши отключения alpha. Pause/hide/resize сбрасывают
измерение; скрытая Canvas не рендерит. Во всех режимах те же дополнительные
резидентные данные, поэтому сравнение с другим JAR менее изолировано.

Все182 класса/все assets immutable Tex3 побайтно сохранены (SHA-256 baseline
`8617f348e04f4b10c03b0049e60f2e92c41532d6939546ad96f6e44d11aa6880`).
Добавлены9 классов и новый manifest, отдельное имя MIDlet. Карта/WTEX/UV/VLA/PNG,
4 кадра реки/скорость6/mode7, конфиги и production sources не менялись.
[Tex3](../downloads/Quantum_StaticRoom_Tex3.jar) и
[старый Packets A/B](../downloads/Quantum_StaticRoom_Packets.jar) сохранены.

Source и packaged CLDC JAR: **1728** комбинаций (Grid/BVH ×3 позиции ×3 pitch
×24 yaw ×4 river frames). A сравнивается с immutable Tex3, все четыре — как
упорядоченный поток атрибутов/strips/state, B/C также по batch boundaries,
A/D по calls. Независимая tuple-таблица, UV/color seams и настоящая hash collision,
cache/hot uploads, OOM/partial cache/recovery, viewport/pose/keys, lifecycle,
coarse часы и усреднение стадий. 15576 river-strip сравнений. Resource audit,
class47.0/CLDC preverify, hashes и детерминированная сборка отдельно.
