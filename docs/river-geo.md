# Карта с рекой: цена геометрии — far и порог по экранному радиусу (F / L)

Отдельный MIDlet: [JAR](../downloads/Quantum_RiverMap_Geo.jar) ·
[JAD](../downloads/Quantum_RiverMap_Geo.jad) ·
[отчёт](../downloads/Quantum_RiverMap_Geo.build-report.json).

Продолжение [апскейл-диагностики](river-upscale.md) после её телефонного
результата. Доставка кадра та же самая, тот же HUD-подход и те же окна
замера; renderer — исходный форк `RiverPixelMesh` из опубликованной
[pixel-сборки](river-pixel.md) с **в точности одним** новым механизмом —
клеточным LOD по экранному радиусу. Геометрия, GRID-отбор, текстуры, свет,
река, near128/far60000/FOV74/DMODE9, alpha/depth и pump — прежние. База
остаётся неизменным Perspective-родителем; классы pixel/upscale JAR-ов в
сборку **не входят** (только новые классы `RiverGeo*`).

## Зачем эта сборка

Из телефонных замеров выведена модель **R ≈ 30 мс фикс + ~74 мс × площадь
экрана**. Апскейл снял масштабный член: S50 UP даёт R 50 и 9.1 FPS против
R109/FPS7.0 у S100. Фиксированный член ~30 мс при S50 теперь составляет
~60% кадра и стал новым главным объектом. Его кандидаты — настройка
сцены и цена по каждому пропущенному треугольнику: сколько из ~30 мс можно
снять, пропуская меньше геометрии. Два рычага, оба консервативные:

* **F (клавиша 7): far 60000 → 40000 → 20000.** Усекает только проекцию и
  фрустум M3G на текущий кадр. Дальняя граница в умолчании и так ниже
  настроенной в карте (68500), поэтому это ужатие, а не опция.
* **L (клавиша 9): порог отсевания GRID-клеток по экранному радиусу
  0 → 8 → 16 px** (пиксели текущего render-viewport). Для каждой занятой
  клетки считается проекция сферы полного AABB клетки на текущий фокус
  рендера; если сфера целиком есть, а её экранный радиус меньше `L`,
  клетка не ставится в очередь. Клетка с камерой внутри сферы не режется
  никогда. Значения считаются в double из текущего мира камеры, так что
  сдвигов FP-преобразования нет; радиус клетки — полудиагональ её полных
  границ (вычислен один раз при построении, кросс-клеточные грани
  закладывают запас — отсев консервативен).

При L0 поведение побайтно совпадает с родителем: тестовый контракт
прогоняет 144 позы и требует совпадения всего потока нативных вызовов,
счётчиков треугольников/углов/VB и селектора. F меняет лишь проекцию,
поэтому для него зафиксирован контракт «упорядоченное подмножество»
F60K-выборки без добавления и без перестановки.

## Режимы и клавиши

HUD — две строки: режим/FPS и `T/N/R/C/I` (добавлен **T** — треугольники,
пропущенные в последнем замеренном кадре). Подпись режима вида
`S50 UP F60K L0 B`:

* `1` — BASE: S100 DIR F60K L0 B (контроль как в pixel/upscale плечах)
* `0` — S100 → S75 → S50 → S25 (остальные ручки сохраняются)
* `3` — DIR ⇄ UP (та же доставка, что в апскейл-сборке)
* `7` — F: far 60000 → 40000 → 20000
* `9` — L: 0 → 8 → 16 px
* `*` — уровень фильтрации B(base) ⇄ M(nearest mip, хинт — на E65 даёт ~5-6%)
* `5` — домой (ручки сохраняются)
* `2/8`, `4/6` — движение; `#` — выход

Стоя на месте — `T` опубликованного окна плюс T последнего кадра, `N`/`R` —
наличие стабильного плато.

## Методология для телефона (Nokia E65, та же близкая поза)

1. Контроль: **S100 DIR F60K L0** против контроля апскейла (7.0 / R112):
   форк не исказил плато.
2. Главная мерка: **S50 UP** во всех девяти комбинациях F×L
   (базовое плечо S50 UP F60K L0: 9.1 / T63 / R50 / C33 / I109).
   Треугольники в кадре фиксируют количество механики, поэтому ожидаемые
   шкалы: T(F20K) срезает дальние клетки сельской картинки, T(L16) — мелкие
   клетки по краям дома.
3. Производная: ΔR/ΔT между соседними ручками — орубая цена пропущенного
   треугольника при неизменной заливке (glue code при том же пиксельном
   потоке). Сравнимое с Fill-моделью разложение покажет, укладываемся ли
   мы под прогноз: если цена по треугольнику почти нулевая, весь фикс-30 —
   константный setup/движок, а не пропуск небес.

Никакой производственный код игры при этом не затрагивается; то, что
окажется рабочим на телефоне, потом обсуждается отдельно.

## Этап десктопной верификации (пройден)

* `tests/river_geo/run.py`: **PASS 2397 проверок / 216 поз·кадров реки** в
  обоих режимах — из исходников и из упакованного CLDC JAR
  (native double-контракт, не растровый эталон и не телефонный FPS).
  Контракты: 144-позовая побайтовая эквивалентность родителю при F60K L0,
  монотонность T по F и L, упорядоченное подмножество выборок, реальное
  срабатывание F20K и L16 хотя бы на одном из прогоняемых ракурсов,
  отсутствие радиус-отсечений при L0, восстановление счётчиков после
  возврата ручек, идентичность UP/DIR-геометрии, доставки и окон статистики.
* `tests/resources/test_river_geo.py`: релизный аудит JAR/JAD/отчёта —
  только десять новых классов `RiverGeo*`, ни один байт родителей не тронут
  (кроме манифеста), классы 1.3 (47.0), контрольные суммы родительских
  исходников зафиксированы.
* Сборка побайтно воспроизводима: повторный прогон билдера даёт тот же
  SHA256.

## Тулчейн-сноска

Эфемерный тулчейн восстановлен (jdk4py 25.0.2.1, ECJ 3.16.0 из npm
`coc-java@1.0.0`, api jar'ы и ProGuard из `vipaoL/j2me-build-tools`).
Новые классы наследуют `getWidth/getHeight` от `Displayable`, что
разрешается идентично на реальном MIDP 2.0 устройстве; pixel-классы в
JAR не упакованы.
