# E65 shot audio probe v1.0.1 — deferred init experiment

This isolated experiment tests a hypothesis, not a confirmed fix. v1.0.0 played one shot and the worker panicked E32USER-CBase 46. In v1.0.1 `MapcInitComplete` only records the result; the existing 20 ms worker poller handles it and calls `Play()` after the callback has unwound. Play-completion handling remains deferred as in v1.0.0. This candidate adds screen counters, whose aligned shared words use SDK-provided atomic operations; those diagnostic operations can themselves affect timing. No game code is modified. The probe opens the shot on demand and does not play music or preload reload, unlike the game. A passing result therefore cannot establish a game fix.

## Test on E65

1. Uninstall **only the old Shot Audio Probe v1.0.0**, not the game. This package uses the same application/package identity but a new self-signed certificate and cannot be assumed to upgrade across certificates. Install v1.0.1 to **phone memory C:**. The package installs only its unique `C:\data\q41_probe_shot.wav`, not the game's WAV. If the phone refuses the test certificate, stop; do not weaken device security.
2. Launch **Shot Audio Probe**; confirm the screen says `SHOT PROBE v1.0.1`. Press 5 once and wait three seconds. Photograph the full screen, note whether sound played. If still running, press 5 several times with pauses; photograph again and report the number of audible shots and any panic or app exit. Escape/Back exits.
3. The display shows `O` (shot open was requested), `I` (init callback error), `P` (number of Play calls entered / returned), `C` (play-complete callbacks), `E` (last completion error), and `H` (completion events handled by the poller). Error `9999` means no callback recorded, not a Symbian error. `0` means that callback reported success, not proof of physical sound output. Counters remain visible after worker panic; a whole-process exit can prevent screen reporting. Photo plus listening report are needed.
