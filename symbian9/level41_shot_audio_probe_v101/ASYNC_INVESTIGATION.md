# Shot probe: asynchronous scheduler investigation

## Observations on E65

v1.0.1 reported `O:1 I:0 P:1/1 C:0 E:9999 H:0` and the worker panicked `E32USER-CBase 46` after one audible shot. Therefore initialization succeeded and `Play()` returned; no application `MapcPlayComplete` callback was recorded. The trace does not locate the instruction or request that generated the stray signal. Deferring init handling did not resolve this isolated failure. v1.0.0 (without the v1.0.1 trace counters) also panicked 46, so the counters are not necessary for reproducing the observed class of failure, although they can affect timing in v1.0.1.

## Source-level findings

- The probe's worker creates an installed `CActiveScheduler` and adds `CQuantumLevel41AudioPoller`. The poller issues `RTimer::After(iStatus, ...)` then `SetActive()` and reschedules at the end of `RunL()`. There is no explicit `RequestComplete` or `RequestSignal` in the probe worker source. This is not proof that timer setup, shared runtime, or a system/library request is correct.
- Independent later Symbian source `SymbianSource/oss.FCL.sf.os.kernelhwsrv` commit `0c3208650587ac0230aed8a74e9bddb5288023eb`, `kernel/eka/euser/cbase/ub_act.cpp`, shows a scheduler waiting for a thread request signal and looking for a registered active object with a completed request; if none is found it raises `EReqStrayEvent`. `User::WaitForRequest` in `kernel/eka/euser/us_exec.cpp` adjusts the request semaphore for other completions encountered while synchronously waiting. This explains why a signal and the actual request lifetime matter; it does not identify the missing event in this E65 ROM.
- Later open Symbian source `SymbianSource/oss.FCL.sf.os.mmaudio` commit `a39c075cce88671b23d13598fda2f7cbf008f3bb`, `mmlibs/mmfw/src/Client/Audio/mmfclientaudioplayer.cpp`, shows the generic player path `Play()` -> `DoPlay()` -> controller Prime/SetPosition/Play, plus a separate playback-complete event path to `MapcPlayComplete`. These sources are reference material from a later release, not a verified source match for E65's ROM. The device trace cannot establish which internal operation or signal failed.
- SDK 0.3.0 pinned source `hpnkv/symbian-platform` commit `b105f752f84d1b5640052f64c4a703017810d7b8`, `cpp/symbian/runtime/legacy_atomic_ops.cc`, implements 32-bit atomics using a shared SWP lock and `User::After(0)` under contention. v1.0.1 adds these atomics for instrumentation. Any influence on timing or request signals in this run is unproven; v1.0.0 also had the panic. These atomics should not be silently treated as zero-cost or as proven cause.

## Discriminating next experiment (not implemented)

Build an isolated A/B test using the same WAV and MDA player, with worker `RTimer` poller removed from the audio thread. Use ordinary MDA callbacks and a separate request-completion-based trigger whose status belongs to a correctly registered active object, with strict cancellation and no cross-thread writes to worker state. Compare against a matched poller-enabled control; record initialization, Play entry/return, callback, worker exit and exact user-observed audibility. Include a timer-only control and an open-without-play control to separate basic poller operation from player activity. A no-poller pass would implicate an interaction, not prove whether the application, SDK/runtime, or ROM is responsible; failures in both would keep the MDA/ABI/runtime hypotheses open. Avoid changing game source or claiming repair before E65 testing. An independent ABI/ordinal comparison against the E65 ROM and relevant legacy headers remains necessary.
